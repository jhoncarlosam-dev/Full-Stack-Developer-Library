Biblioteca de contingencia full stack

Esta carpeta existe para cuando no puedas preguntarle a una IA. Aquí está el patrón, el comando y el arreglo del error habitual para construir una aplicación web completa y dejarla funcionando.

Sigue el orden del Full Stack Roadmap (principiantes, 2026). El texto es propio. El mapa solo aporta la lista de temas y el orden.

Stack de esta biblioteca

Un solo camino, el que el roadmap recomienda:

HTML, CSS, JavaScript, Tailwind, React, npm, Git, GitHub, Node.js, PostgreSQL, API REST, Redis, JWT, Linux, AWS básico (EC2, VPC, S3, Route 53, SES), Monit, GitHub Actions, Ansible y Terraform.

Si una tarea también se hace con otra herramienta, se nombra en una línea. No hay un segundo tutorial.

Cómo buscar

  1. Tienes un error o algo que no se comporta como esperabas: abre 00-indice-de-sintomas.md y busca palabras del mensaje (CORS, EADDRINUSE, 401, relation does not exist).
  2. No sabes en qué parte del mapa estás: abre 00-mapa-del-roadmap.md.
  3. El fallo es confuso y no cabe en una ficha: sigue 00-metodo-sin-ia.md y después 19-depuracion.md.
  4. Vas a exponer la app a internet o a guardar contraseñas: lee 20-seguridad-minima.md antes de copiar un ejemplo.

En el editor, la búsqueda de todo el proyecto (en Cursor o VS Code: Ctrl+Shift+F) recorre todos los archivos. Busca el texto literal del error, entre comillas si hace falta.

También puedes abrir abrir.html con doble clic. Tiene buscador y no necesita servidor ni internet. Si cambias un markdown, vuelve a generar el visor con:

node construir-visor.js

Qué significa cada nivel

El significado es el mismo en todos los archivos.

  • Básico. El mínimo que funciona en tu máquina. Un archivo, un comando, un resultado que puedes ver.
  • Intermedio. El patrón de una aplicación pequeña de verdad: los datos persisten, los errores se manejan, las piezas están conectadas.
  • Avanzado. Lo que se rompe cuando hay usuarios reales, y el arreglo concreto: seguridad, rendimiento, despliegue, recuperación. No es un curso de sistemas distribuidos.

Empieza por el básico aunque creas que ya lo sabes. En contingencia, el olvido del básico es lo que más tiempo quita.

Qué no hace falta memorizar

Memoriza el orden del mapa, el método de depuración y los comandos que usas cada semana (git status, npm run, psql, systemctl). El resto se busca aquí o en la documentación oficial.

Qué practicar en cada tramo

No avances de tramo con el checkpoint anterior solo leído. Tiene que haber un resultado en tu máquina.

  1. Una página estática tuya.
  2. Esa página con una lista que se agrega y se borra, en JavaScript puro.
  3. Un paquete de npm usado de verdad y un repositorio en GitHub con una pull request.
  4. La misma lista en React y Tailwind, o saltar este punto y volver antes del paso 6.
  5. Un script de Node y después notas en PostgreSQL con alta, lectura, cambio y borrado.
  6. La misma lista con API, login y una caché. Eso es la app completa.
  7. Esa app en un servidor con HTTPS. Primero en local con los mismos comandos de Linux; AWS solo cuando el local ya funciona.
  8. Un reinicio automático, un workflow que corre pruebas, y los archivos de Ansible y Terraform del servidor que ya entendiste a mano.

Método sin IA

Cuando algo falla, el orden importa más que la memoria. Recorre estos pasos en este orden. No saltes al paso 4 porque el mensaje "se parece" a un error que viste la semana pasada.

Detalle de herramientas (consola, logs, curl, SQL) en 19-depuracion.md. Esta página es solo la secuencia.

1. Reproducir

Escribe, en una frase, qué haces y qué ocurre.

Abro /notas, recargo, y la API responde 401.
El formulario de alta no hace nada al pulsar Guardar.
npm test falla solo en GitHub, en mi máquina pasa.

Si no puedes repetirlo, no lo arregles todavía. Anota cuándo apareció: al recargar, solo en el teléfono, solo después del último commit, solo en el servidor.

2. Leer el error literal

Copia la primera línea del error, no el párrafo final. La causa suele estar arriba del todo o en la primera línea que menciona tu archivo, no en node_modules.

Busca ese texto en 00-indice-de-sintomas.md. Si está, sigue esa ficha y vuelve aquí solo si el arreglo no cuadra con lo que ves.

Ignora, de momento, consejos genéricos del tipo "reinicia el ordenador". Reiniciar es el paso 6, no el paso 2.

3. Separar la capa

Un fallo vive en un solo sitio hasta que demuestres lo contrario. Tacha capas con una prueba pequeña.

Ejemplo: la pantalla dice "no se pudieron cargar las notas". En la pestaña Red la petición devuelve 500. curl devuelve el mismo 500. Entonces el frontend está descartado. El log de Node dice relation "notes" does not exist. La capa es PostgreSQL, no React.

4. Cambiar una sola cosa

Un cambio por intento: una línea, una variable de entorno, un índice, un puerto. Anota qué cambiaste. Si no mejora, deshazlo antes del siguiente intento.

Dos cambios a la vez te dejan sin saber cuál funcionó. Al día siguiente no podrás repetirlo.

5. Comprobar

La comprobación es el mismo gesto del paso 1, más el caso vecino que podría haberse roto.

  • Si arreglaste el alta, prueba también el listado y el borrado.
  • Si arreglaste el login, recarga la página y llama a una ruta protegida.
  • Si arreglaste el servidor, mira el log después de reiniciar, no solo la primera respuesta.

Cada ficha tiene una sección "Cómo comprobar". Úsala. Una pantalla que "parece" arreglada no cuenta.

6. Recién entonces, lo mecánico

Si la capa ya está aislada y el cambio dirigido no bastó:

  • Reinicia solo el proceso implicado, no todo el sistema.
  • Confirma que estás en el directorio y la rama que crees (pwd, git status).
  • Confirma que el .env que lee el proceso es el que editaste.
  • Confirma que el navegador no muestra una versión vieja: recarga forzada, o una ventana privada.

Qué no hacer

  • No pegues el error en cinco sitios y apliques el primer comando que veas. Un DROP TABLE, un git reset --hard o un terraform destroy no son pasos de diagnóstico.
  • No desactives HTTPS, la autenticación o CORS "para ver si arranca" y lo dejes así. El atajo de diagnóstico se anota y se revierte. La versión que se publica está en 20-seguridad-minima.md.
  • No compares tu máquina con el servidor hasta haber ejecutado el mismo comando en los dos. "En local funciona" casi siempre es otra versión del código, otra variable o otra base de datos.

HTML

HTML describe qué hay en la página: títulos, párrafos, enlaces, imágenes, formularios. No pinta el color ni decide qué pasa al pulsar un botón. El color es 02-css-y-tailwind.md. El botón es 03-javascript.md.

Cuándo usarlo y cuándo no

Úsalo siempre que haya una pantalla. Aunque más adelante uses React, el resultado que ve el navegador sigue siendo HTML.

No lo uses para guardar datos ni para esconder un secreto: cualquiera puede ver el código fuente. Una contraseña escrita en el HTML no está escondida.

Básico

Una página que se abre con doble clic, sin servidor.

index.html

<!doctype html>
<html lang="es">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Notas de Ada</title>
  </head>
  <body>
    <header>
      <h1>Notas de Ada</h1>
      <nav>
        <a href="#lista">Lista</a>
        <a href="#nueva">Nueva</a>
      </nav>
    </header>
    <main>
      <section id="lista">
        <h2>Pendientes</h2>
        <ul>
          <li>Revisar el formulario</li>
          <li>Subir la página a un sitio estático</li>
        </ul>
      </section>
      <section id="nueva">
        <h2>Nueva nota</h2>
        <form action="#lista">
          <label for="titulo">Título</label>
          <input id="titulo" name="titulo" type="text" required maxlength="80">
          <button type="submit">Guardar</button>
        </form>
      </section>
    </main>
  </body>
</html>

Qué tiene que estar, aunque la página sea pequeña:

  • <!doctype html> para que el navegador no entre en modo antiguo.
  • lang="es" para lectores de pantalla y correctores.
  • charset="utf-8" para tildes y eñes.
  • viewport para que el teléfono no la muestre empequeñecida. Sin esta línea, el CSS del móvil "no funciona" y el fallo es el HTML.
  • Un solo h1. Los h2 son secciones, no "letras más grandes". El tamaño se cambia con CSS.
  • Cada input con su <label for="id">. El name es lo que viaja al enviar el formulario. El id es lo que usa el label.

Comprueba: abre el archivo en el navegador. El título de la pestaña es "Notas de Ada". Pulsar "Lista" salta a la lista.

Intermedio

Formulario que un servidor puede entender, con los tipos de campo correctos y mensajes del propio navegador.

<form action="/notas" method="post">
  <label for="titulo">Título</label>
  <input id="titulo" name="titulo" type="text" required maxlength="80" autocomplete="off">

  <label for="detalle">Detalle</label>
  <textarea id="detalle" name="detalle" rows="4" maxlength="2000"></textarea>

  <label for="cuando">Fecha</label>
  <input id="cuando" name="cuando" type="date">

  <fieldset>
    <legend>Prioridad</legend>
    <label><input type="radio" name="prioridad" value="baja" checked> Baja</label>
    <label><input type="radio" name="prioridad" value="alta"> Alta</label>
  </fieldset>

  <button type="submit">Guardar</button>
</form>

Reglas que evitan bugs de los que luego se culpa a JavaScript:

  • method="post" cuando creas o cambias datos. get mete los campos en la URL y se guarda en el historial.
  • button type="submit" dentro del formulario. Un <button> sin tipo también envía. Un botón que solo abre un diálogo lleva type="button", si no, envía el formulario.
  • Radios del mismo grupo comparten name y se distinguen por value.
  • required y maxlength son la primera barrera. El servidor tiene que repetir la validación: el HTML se puede saltar. Ver 09-api-rest.md.

Lista de verdad, no una tabla para maquetar:

<table>
  <caption>Notas abiertas</caption>
  <thead>
    <tr><th>Título</th><th>Prioridad</th></tr>
  </thead>
  <tbody>
    <tr><td>Revisar el formulario</td><td>Alta</td></tr>
  </tbody>
</table>

La tabla es para datos en filas y columnas. Una página de presentación se arma con header, main, section y CSS.

Imágenes y enlaces con ruta relativa al archivo:

<img src="img/portada.jpg" alt="Cuaderno abierto sobre una mesa" width="800" height="450">
<a href="notas/abril.html">Notas de abril</a>
<a href="https://developer.mozilla.org/es/docs/Web/HTML" rel="noreferrer">MDN</a>

alt describe la imagen para quien no la ve. Si la imagen es decorativa, alt="". width y height reservan el hueco y la página no salta al cargar.

Avanzado

Lo que se rompe cuando la página la usa otra persona, un lector de pantalla o un buscador.

Formulario que no depende solo del color y del placeholder:

<label for="correo">Correo</label>
<input
  id="correo"
  name="correo"
  type="email"
  required
  autocomplete="email"
  aria-describedby="correo-ayuda"
>
<p id="correo-ayuda">Lo usamos solo para avisarte de un cambio.</p>
  • El placeholder no sustituye al label: desaparece al escribir.
  • autocomplete con el valor estándar (email, current-password, new-password) es lo que permite al gestor de contraseñas rellenar solo.
  • No pongas la contraseña en un <input type="text">. Usa type="password" y, en el servidor, un hash. Ver 20-seguridad-minima.md.

Contenido que se inyecta más tarde (cuando llegue JavaScript) necesita un hueco anunciado:

<div id="avisos" role="status" aria-live="polite"></div>
<ul id="lista"></ul>

Si metes HTML escrito por el usuario con innerHTML, ese usuario puede ejecutar código en la sesión de otra persona. En el nivel avanzado el texto de una nota se inserta como texto, no como HTML. El patrón está en 03-javascript.md.

Errores frecuentes

La página sale en blanco y la consola está vacía

Causa habitual: el archivo que abres no es el que editaste, o el HTML está tan roto que el navegador no muestra el body (un <head> sin cerrar y el contenido quedó dentro del head, que no se pinta).

Arreglo: clic derecho, "Ver código fuente". Si no está tu <h1>, estás mirando otro archivo. Si está, busca una etiqueta abierta sin su cierre justo antes del contenido que falta. El inspector (F12, pestaña Elementos) muestra el árbol ya interpretado: ahí se ve si tu main acabó dentro de head.

Si la consola tiene un error rojo, el caso es otro: 03-javascript.md.

El formulario recarga la página y pierde lo escrito

Causa habitual: el botón es type="submit" y no hay JavaScript que haga preventDefault, o sí lo hay pero el script falló antes de registrarse.

Arreglo de diagnóstico: quita el script. Si al enviar se recarga, el HTML está haciendo su trabajo. Para quedarte en la página, el manejador tiene que ejecutarse. Patrón en 03-javascript.md. Mientras tanto, pon method y action reales: si el script falla, el navegador aún puede enviar los datos al servidor.

La imagen sale rota

Causa habitual: la ruta se calculó desde el navegador, no desde el archivo. src="img/portada.jpg" es relativo a la URL de la página. Si la página es /notas/abril.html, el navegador pide /notas/img/portada.jpg.

Arreglo: en la pestaña Red, mira la URL exacta que devolvió 404. Muévela a esa carpeta o cambia el src a una ruta desde la raíz del sitio: src="/img/portada.jpg". En un sitio con subcarpetas, la barra inicial evita el error. Comprueba también mayúsculas: Portada.jpg y portada.jpg son archivos distintos en Linux.

El enlace no lleva a ningún lado o baja un archivo

Causa habitual: href vacío, href="#" o una ruta a un archivo sin extensión que el servidor ofrece como descarga. Otro caso: usaste <button> con un href, que no existe; el atributo se ignora.

Arreglo: un enlace de verdad es <a href="abril.html">. Un control que no navega es <button type="button">. Si al pulsar se descarga, el servidor no está sirviendo ese archivo como página; abre la URL directa y lee el código de estado en la pestaña Red.

Cómo comprobar

  1. Abre index.html con doble clic o con un servidor estático (npx serve), que es más fiel a una URL real.
  2. Recorre la página solo con el teclado: Tab debe entrar a cada enlace y cada campo, en un orden que se entiende.
  3. Envía el formulario vacío. El navegador debe señalar el campo required.
  4. Cambia el ancho de la ventana. Sin CSS todavía se verá simple; no debe haber texto cortado por falta de viewport.
  5. Desactiva CSS e imágenes en el inspector o lee el HTML en voz alta. Si no se entiende, la estructura no está lista para el checkpoint.

Si esto no alcanza

Busca en MDN, en español o en inglés:

  • mdn html forms
  • mdn input types
  • mdn viewport meta
  • mdn img alt
  • mdn content security policy cuando vayas a publicar

CSS y Tailwind

CSS decide cómo se ve el HTML: tamaño, color, espacio y si cabe en el teléfono. Tailwind es un conjunto de clases ya definidas (flex, p-4, text-lg) para no escribir un archivo CSS enorme en cada pantalla. El mapa deja Tailwind para junto a React, y se puede retomar después del backend. El CSS de esta página hace falta antes: sin él la página estática del checkpoint se lee, pero no se usa.

Cuándo usarlo y cuándo no

Usa CSS en cuanto haya más de un bloque en la página. Usa Tailwind cuando el proyecto ya tiene Node y un empaquetador (Vite, en la ficha de React). No hace falta Tailwind para el checkpoint de la página estática.

No uses una tabla, ni position: absolute en todo, para "colocar cosas". Eso se rompe en cuanto cambia el texto o el ancho.

Básico

En el <head> del HTML:

<link rel="stylesheet" href="estilos.css">

estilos.css, al lado de index.html:

* { box-sizing: border-box; }

body {
  margin: 0;
  font-family: system-ui, sans-serif;
  line-height: 1.5;
  color: #1c1917;
  background: #fafaf9;
}

main {
  max-width: 40rem;
  margin-inline: auto;
  padding: 1.5rem;
}

label, button { display: block; }
input, textarea, button { width: 100%; max-width: 24rem; }

.nota {
  border: 1px solid #d6d3d1;
  border-radius: 0.5rem;
  padding: 0.75rem 1rem;
  margin-block: 0.75rem;
}

Tres decisiones que evitan la mitad de los bugs de maquetación:

  • box-sizing: border-box hace que width incluya el relleno y el borde. Sin esto, un bloque de 100% más un padding se sale del padre.
  • max-width y margin-inline: auto centran la columna sin posiciones absolutas.
  • system-ui usa la letra del sistema. No dependes de una fuente descargada para que el texto se lea.

Clases para lo que se repite (.nota). El estilo suelto en style="" solo para una prueba que vas a borrar.

Comprueba: el texto no toca los bordes de la ventana y los campos no se salen de la columna.

Intermedio

Layout que aguanta un título largo y un ancho estrecho. Primero en CSS. El equivalente Tailwind está debajo, para cuando llegues a Vite.

.barra {
  display: flex;
  flex-wrap: wrap;
  gap: 0.75rem;
  align-items: center;
  justify-content: space-between;
}

.rejilla {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(14rem, 1fr));

Tailwind, cuando el proyecto ya es el de 06-react.md. Instalación mínima con Vite:

import react from "@vitejs/plugin-react";

El mismo layout, en clases:

<header class="flex flex-wrap items-center justify-between gap-3">
  <h1 class="text-xl font-semibold">Notas</h1>

    <a class="underline" href="#lista">Lista</a>

No mezcles un CSS propio enorme con Tailwind "por si acaso". Elige uno por proyecto. En esta biblioteca, la página estática va en CSS y la app React va en Tailwind.

Avanzado

Lo que se rompe en producción no es el color: es el contraste, el foco y el contenido que crece.

:focus-visible {
  outline: 3px solid #1d4ed8;
  outline-offset: 2px;
}

body { font-size: 1rem; }
h1 { font-size: clamp(1.5rem, 2vw + 1rem, 2.25rem); }
  • No quites el outline del foco sin poner otro. Quien usa teclado deja de ver dónde está.
  • Texto sobre fondo: si dudas, fondo claro y texto casi negro. El gris claro sobre blanco falla en un móvil al sol.
  • clamp evita un título gigante en el escritorio y diminuto en el teléfono, sin cortar palabras con un alto fijo.
  • No fijes alturas en tarjetas (height: 120px) si el título puede ocupar dos líneas. Usa min-height o deja que crezcan.
  • Una animación no es obligatoria. Si la usas, respeta prefers-reduced-motion para quien pidió al sistema menos movimiento.

Errores frecuentes

Los elementos se enciman o se salen de la pantalla

Causa habitual: un ancho en píxeles mayor que la ventana, un position: absolute sin padre relativo, o un flex hijo con min-width: auto que no quiere encogerse (pasa mucho con una palabra larga o un <pre>).

Arreglo: en el inspector, mira la caja del elemento que se sale. Si el ancho es fijo, cámbialo a max-width: 100%. En una fila flex, al hijo que empuja ponle min-width: 0 (en Tailwind, min-w-0). Quita el absolute y vuelve al flujo: flex o grid con gap.

En el teléfono se ve roto y en el escritorio no

Causa habitual: falta <meta name="viewport" content="width=device-width, initial-scale=1">, o escribiste las media queries al revés (estilos de escritorio como base y el móvil no los pisa).

Arreglo: confirma el viewport en 01-html.md. En Tailwind, diseña primero sin prefijo (el ancho estrecho) y añade sm: solo donde el escritorio cambia. En CSS propio, prueba el ancho en el inspector (modo dispositivo) a 360px antes de dar el layout por bueno.

Las clases de Tailwind no se aplican

Causa habitual, en este orden:

  1. No importaste Tailwind en el CSS de entrada, o ese CSS no está importado desde main.jsx.
  2. El plugin no está en vite.config.js y tampoco hay un tailwind.config.js si usas la versión antigua (v3). La v4 usa @tailwindcss/vite y @import "tailwindcss". No mezcles las instrucciones de las dos versiones.
  3. El nombre de la clase está armado a trozos en una cadena: ` className={text-${color}-600} `. Tailwind no lo ve al construir y no genera la clase.

Arreglo: deja la clase completa escrita en el archivo (text-red-600) o guárdala entera en un mapa. Reinicia npm run dev después de tocar la config. En el inspector, si la clase está en el HTML pero no hay regla CSS, el generador no la incluyó.

Cómo comprobar

  1. A 360px, 768px y ancho completo no hay scroll horizontal. El inspector lo marca si existe.
  2. Tab muestra dónde está el foco en enlaces y botones.
  3. Un título de 80 caracteres no tapa el botón de al lado: la fila salta de línea.
  4. Si usas Tailwind, borra una clase y recarga: el cambio se ve. Si no se ve, no está conectado, aunque el archivo "esté bien".

Si esto no alcanza

En MDN: mdn flexbox, mdn grid auto-fit, mdn box-sizing, mdn focus-visible.

En la documentación de Tailwind: tailwind installation vite, y el nombre exacto de la clase (tailwind min-w-0, tailwind responsive sm).

JavaScript

JavaScript es lo que hace cambiar la página sin pedir otro HTML completo: leer un campo, añadir una fila, pedir datos a una API. En el navegador trabaja con el DOM (el árbol de etiquetas ya construido). En el servidor, el mismo lenguaje se usa con Node; eso es 07-nodejs.md. Aquí es solo el navegador.

Cuándo usarlo y cuándo no

Úsalo cuando el HTML y el CSS ya muestran la pantalla y falta comportamiento. No lo uses para lo que HTML ya hace solo: saltar a una sección, marcar un campo obligatorio, enviar un formulario a una URL.

Si copias un ejemplo y no sabes qué línea corresponde a tu botón, no lo pegues entero. Localiza el id y el evento, y adapta solo eso.

Básico

El script va al final del body para que el HTML ya exista, o en el head con defer:

<script src="app.js" defer></script>

app.js, una lista en memoria que se pinta al pulsar:

const form = document.querySelector("#nueva");
const lista = document.querySelector("#lista");
const titulo = document.querySelector("#titulo");
const notas = [];

form.addEventListener("submit", (event) => {
  event.preventDefault();
  const texto = titulo.value.trim();
  if (!texto) return;

  notas.push({ id: crypto.randomUUID(), texto });
  titulo.value = "";
  pintar();
});

function pintar() {
  lista.replaceChildren();
  for (const nota of notas) {
    const li = document.createElement("li");
    li.textContent = nota.texto;

    const borrar = document.createElement("button");
    borrar.type = "button";
    borrar.textContent = "Borrar";
    borrar.addEventListener("click", () => {
      const i = notas.findIndex((n) => n.id === nota.id);
      notas.splice(i, 1);
      pintar();
    });

    li.append(borrar);
    lista.append(li);
  }
}

Por qué está escrito así:

  • preventDefault evita la recarga del síntoma del formulario.
  • textContent mete texto. innerHTML mete HTML y, con texto de un usuario, es un agujero. No lo uses para notas, nombres o comentarios.
  • crypto.randomUUID() da un id sin instalar nada. El índice del array cambia al borrar; el id no.
  • Un solo sitio pinta (pintar). Si añades y borras tocando el DOM a mano en dos funciones, se desincronizan.

Comprueba: añadir dos notas, borrar la primera, recargar. Al recargar desaparecen. Eso es correcto en este nivel: viven en la variable notas. La persistencia es el nivel intermedio.

Intermedio

Guardar en el navegador, y pedir datos sin congelar la página.

const CLAVE = "notas";

function leer() {
  const crudo = localStorage.getItem(CLAVE);
  if (!crudo) return [];
  try {
    const datos = JSON.parse(crudo);
    return Array.isArray(datos) ? datos : [];
  } catch {
    return [];
  }
}

function guardar(notas) {
  localStorage.setItem(CLAVE, JSON.stringify(notas));
}

localStorage solo guarda strings, solo en ese navegador, y el usuario puede borrarlo. No guardes ahí un token de sesión ni una contraseña. Para datos de varias personas hace falta el servidor y PostgreSQL.

Pedir JSON a una API y mostrar el fallo:

async function cargarNotas() {
  const aviso = document.querySelector("#avisos");
  aviso.textContent = "Cargando…";
  try {
    const respuesta = await fetch("/api/notas");
    if (!respuesta.ok) {
      throw new Error("HTTP " + respuesta.status);
    }
    const notas = await respuesta.json();
    aviso.textContent = "";
    return notas;
  } catch (error) {
    aviso.textContent = "No se pudieron cargar las notas.";
    console.error(error);
    return [];
  }
}

fetch no lanza un error cuando el servidor responde 404 o 500. Hay que mirar respuesta.ok. El catch cubre red caída, CORS que bloquea la lectura y un JSON inválido. El usuario ve una frase; el detalle queda en la consola.

Manda JSON al crear:

await fetch("/api/notas", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ titulo: texto }),
});

Sin el header Content-Type, el servidor puede no interpretar el cuerpo. Ese síntoma está en 09-api-rest.md.

Avanzado

Lo que se rompe con varios clics y con datos que no controlas.

Un envío doble crea dos notas. Desactiva el botón mientras dura la petición:

form.addEventListener("submit", async (event) => {
  event.preventDefault();
  const boton = form.querySelector("button[type=submit]");
  boton.disabled = true;
  try {
    await crearNota(titulo.value.trim());
    titulo.value = "";
    await pintarDesdeServidor();
  } finally {
    boton.disabled = false;
  }
});

finally corre aunque haya error. Si el disabled = false estuviera solo al final del try, un fallo dejaría el botón muerto.

No construyas HTML con los datos:

// Mal: si texto es '<img src=x onerror=alert(1)>', se ejecuta.
lista.innerHTML = notas.map((n) => `<li>${n.texto}</li>`).join("");

El patrón de createElement y textContent del básico aguanta ese texto. Si alguna vez necesitas HTML de una plantilla, los datos van por texto aparte, nunca concatenados.

localStorage se llena (sobre 5 MB) y además es síncrono: un JSON enorme traba la página. Ahí los datos ya no son "borrador local"; son del servidor.

Módulo en el navegador, cuando el archivo crece:

<script type="module" src="app.js"></script>
import { pintar } from "./pintar.js";

Los módulos se cargan en diferido y las variables no quedan globales. Hay que servir la página por HTTP (npx serve); abrir el archivo con doble clic suele bloquear el import.

Errores frecuentes

La página sale en blanco y la consola tiene un error rojo

Causa habitual: una excepción en el script antes de pintar, o un React que se desmonta (ese caso, en 06-react.md). En JS puro, un error en la primera línea del script detiene el resto. La página se ve vacía si el contenido lo iba a crear el script.

Arreglo: lee la primera línea de la consola. Abre el archivo y la línea que indica. Un error típico es llamar a pintar() antes de definirla de una forma que aún no existe, o un import que 404. Arregla esa línea, recarga y mira si aparece el siguiente error. Uno por vez, como en 00-metodo-sin-ia.md.

Cannot read properties of null o de undefined

Causa habitual: querySelector no encontró el elemento y el código hace form.addEventListener. El selector no coincide con el id, o el script corrió antes de que existiera el HTML (falta defer y el script está en el head).

Arreglo: en la consola, ejecuta la misma cadena del querySelector. Si devuelve null, el id del HTML y el del JS no son el mismo, mayúsculas incluidas. Añade una guarda mientras depuras: if (!form) throw new Error("falta #nueva");. El mensaje nuevo es más claro que null.

is not a function

Causa habitual: el nombre no es el que crees. notas.push falla si notas es un objeto, no un array. respuesta.json() falla si llamaste json sobre otra cosa. También pasa al escribir addEventListener mal o al sombrear una función con una variable del mismo nombre.

Arreglo: justo antes de la línea, console.log(typeof notas, notas). typeof de una función es "function". Si es "object" o "string", el valor se transformó antes: un JSON.parse de un objeto, o un campo del formulario en vez del array.

El botón no hace nada

Causa habitual, en orden:

  1. El script no se cargó (404 en la pestaña Red).
  2. Hay un error anterior y esta línea no se llegó a ejecutar.
  3. El botón es type="submit" y estás escuchando click en el botón mientras el submit del formulario recarga la página antes de que veas el efecto.
  4. Escuchas #guardar y el id real es #guardar-nota.

Arreglo: consola limpia, recarga, mira si hay rojo. Pon el escuchador en el submit del formulario, con preventDefault, como en el básico. En la pestaña Elementos, el botón seleccionado muestra sus escuchadores (Events / Listeners).

fetch no entra al .then ni muestra error

Causa habitual: falta el return delante de respuesta.json(), o la función es async y nadie hace await ni .catch. La promesa queda rechazada sin receptor. En Chrome eso aparece como "Uncaught (in promise)", fácil de no ver si la consola está filtrada a Warnings.

Arreglo: usa el try/catch del nivel intermedio alrededor de cada await fetch. Mira la pestaña Red: si la petición ni siquiera sale, la función no se llamó (vuelve al botón muerto). Si sale en rojo por CORS, el arreglo no es del fetch; es del servidor, en 09-api-rest.md.

Cómo comprobar

  1. Consola sin errores al cargar, al añadir y al borrar.
  2. Texto <b>hola</b> se ve como caracteres, no en negrita. Eso confirma que no hay innerHTML.
  3. Dos clics rápidos en Guardar no crean dos notas (nivel avanzado) o, en el básico, al menos no recargan la página.
  4. Con la red en "offline" en el inspector, la carga muestra el aviso y no una pantalla muda.
  5. Recargar conserva las notas solo si ya usas localStorage o el servidor. Si desaparecen y aún estás en el básico, es lo esperado.

Si esto no alcanza

En MDN: mdn querySelector, mdn addEventListener, mdn fetch, mdn async await, mdn localStorage, mdn textContent.

  • El texto se inserta con textContent.

Hecho cuando recargas y entiendes por qué se borra (aún no hay persistencia) y cuando un texto con < y > no altera la página.

Persistir en localStorage es el extra del nivel intermedio, no la condición para pasar.

npm

npm instala librerías y guarda los comandos del proyecto en package.json. Viene con Node. Si node -v y npm -v no imprimen un número, instala Node LTS desde nodejs.org y abre una terminal nueva.

El checkpoint del mapa es usar un paquete externo de verdad, no escribir tu propio validador de correos.

Cuándo usarlo y cuándo no

Úsalo cuando el proyecto tenga más de un archivo de código o necesites una librería. Un index.html con un app.js del checkpoint de interactividad puede seguir sin npm.

No instales un paquete para una función de tres líneas que el lenguaje ya trae (crypto.randomUUID, fetch, URL). Cada dependencia es código ajeno que hay que actualizar.

Básico

En una carpeta vacía del proyecto:

npm init -y
npm install validator

Quedan package.json, package-lock.json y node_modules. node_modules no se sube a Git. El lock sí. Ver 05-git-y-github.md.

package.json, la parte que importa:

{
  "name": "notas",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "node src/cli.js"
  },
  "dependencies": {
    "validator": "^13.15.0"
  }
}

"private": true evita publicar el proyecto en el registro de npm por accidente. "type": "module" permite import en Node. El número de validator será el que npm haya resuelto; no copies el de esta página si el tuyo es más nuevo.

Uso mínimo, src/cli.js:

import validator from "validator";

const correo = process.argv[2] ?? "";
if (!validator.isEmail(correo)) {
  console.error("Correo no válido");
  process.exitCode = 1;
} else {
  console.log("Correo válido");
}
npm run dev -- ada@example.com
npm run dev -- no-es-un-correo

El -- separa los argumentos de npm de los de tu script. Sin él, npm se queda el argumento.

npm install sin nombre, en un proyecto ya creado por otra persona, instala exactamente lo que dice el lock.

Intermedio

Separa lo que corre en producción de lo que solo usas al desarrollar.

npm install express
npm install --save-dev vitest
{
  "scripts": {
    "start": "node src/server.js",
    "dev": "node --watch src/server.js",
    "test": "vitest run"
  }
}
  • dependencies: hace falta para que la app arranque (express, pg, validator).
  • devDependencies: hace falta para escribirla (vitest, vite). En el servidor de producción se instala con npm ci --omit=dev.
  • npm run dev con node --watch reinicia al guardar. No hace falta nodemon para ese caso.
  • npm ci borra node_modules e instala el lock tal cual. Úsalo en CI y en el servidor. npm install puede mover versiones dentro del rango ^ y cambiar el lock.

Versiones: ^13.15.0 acepta 13.x nuevos y no acepta 14.0.0. Para una app tuya, el lock fija el resto. No pongas "*" ni borres el lock "para que instale lo último": eso es cómo un lunes el proyecto deja de arrancar.

Un paquete que solo existe en el navegador se importa desde el frontend (Vite lo empaqueta). Un paquete de Node (pg, express) no se importa en un componente React: fallará en el navegador con fs o net inexistentes.

.gitignore mínimo junto al package.json:

node_modules/
.env
dist/

Avanzado

Lo que se rompe cuando el proyecto vive más de una semana o lo instala otra máquina.

npm ci en el servidor y en GitHub Actions, nunca npm install. El install reescribe el lock si las ramas divergieron; el ci aborta si package.json y el lock no coinciden, que es lo que quieres.

Revisa qué entró:

npm ls --depth=0
npm audit

npm audit lista avisos conocidos. No ejecutes npm audit fix --force a ciegas: puede saltar una versión mayor y romper el proyecto. Lee el aviso. Si el paquete vulnerable es solo de desarrollo y no corre en producción, el riesgo es distinto a si es express.

Actualizar un paquete, de uno en uno:

npm outdated
npm install validator@13
npm test

Si los tests pasan, commiteas package.json y package-lock.json juntos. Nunca uno sin el otro.

El registro de npm puede estar caído o bloqueado. Un install reproducible no depende de "lo que hubiera ese día" gracias al lock. Guardar una copia del lock en Git es la contingencia; no hace falta un espejo propio en este nivel.

Paquetes que piden permisos de compilación nativa (bcrypt compilado, no bcryptjs) necesitan herramientas de C++ en la máquina. En un servidor mínimo eso falla con un error de node-gyp. Para contraseñas, bcryptjs es JavaScript puro y evita ese fallo. La comparación está en 20-seguridad-minima.md.

Errores frecuentes

Cannot find module

Causa habitual:

  1. No corriste npm install en esa carpeta.
  2. El nombre del import no es el del paquete (import express from "Express" falla: en Linux el nombre es sensible a mayúsculas).
  3. Importas un archivo tuyo sin ./. import { x } from "utilidades" busca un paquete, no ./utilidades.js.
  4. Estás en otro directorio: el package.json no es el de arriba.

Arreglo: npm ls nombre-del-paquete. Si dice empty o invalid, instálalo. Si el import es tuyo, añade ./ y la extensión .js cuando uses "type": "module". Node no adivina la extensión en ESM.

ERESOLVE, el install no termina

Causa habitual: dos paquetes piden versiones incompatibles del mismo dependiente. npm 7+ se niega a instalar un árbol que no cuadra, en vez de callar.

Arreglo: lee el bloque While resolving del error. Identifica qué paquete pediste tú (el de arriba) y cuál choca. Opciones, en orden: subir o bajar ese paquete a una versión que declare rangos compatibles; quitar el que no necesitas. --legacy-peer-deps es un último recurso temporal, no la solución que se commitea sin saber qué conflicto ignoraste. Después de resolver, npm ls no debe mostrar invalid.

Conflicto en package-lock.json

Causa habitual: dos ramas instalaron paquetes distintos y Git no puede unir el JSON del lock.

Arreglo: no edites el lock a mano. Quédate con una de las dos versiones del archivo (git checkout --ours package-lock.json o --theirs), abre package.json y deja a mano las dependencias que de verdad quieres de las dos ramas, y corre npm install para regenerar el lock. Luego npm test. Detalle de conflictos de Git en 05-git-y-github.md.

Missing script

Causa habitual: npm start y en package.json el script se llama dev, o estás en una subcarpeta sin package.json.

Arreglo: npm run sin nombre lista los scripts que existen. Desde la raíz del proyecto (donde está el package.json), npm run dev. npm start y npm test son atajos de scripts con ese nombre exacto; el resto exige npm run.

Cómo comprobar

  1. Borra node_modules y corre npm ci. El proyecto vuelve a instalarse sin tocar el lock.
  2. npm run muestra dev y test.
  3. Una máquina nueva, o tu misma tras clonar, no necesita copiar node_modules. Con el lock basta.
  4. El paquete del checkpoint se usa en una ruta real del programa (validar un correo, formatear una fecha), no solo está instalado.

Si esto no alcanza

Documentación de npm: npm ci, npm install save-dev, package.json scripts, package-lock.json.

El error de ERESOLVE se busca con la primera línea literal, más el nombre de los dos paquetes que chocan.

Checkpoint — paquetes externos (30 a 45 minutos)

En el proyecto de la lista de notas, o en el script de 07-nodejs.md si ya llegaste allí:

  • npm init, un package.json con "private": true y al menos un script.
  • Un paquete externo usado para una decisión real (por ejemplo validator para el correo, o date-fns para mostrar una fecha legible).
  • node_modules ignorado y el lock incluido en Git cuando des el paso de 05-git-y-github.md.

Hecho cuando npm ci en una carpeta recién clonada (o tras borrar node_modules) deja el comando npm run dev funcionando.

Git y GitHub

Git guarda el historial en tu máquina: qué cambió, quién y cuándo, y te deja volver. GitHub es una copia de ese historial en internet, más la revisión del trabajo entre personas (pull request). El checkpoint del mapa es ese trabajo en equipo, aunque el "equipo" seas tú en dos ramas.

Cuándo usarlo y cuándo no

Empieza a usarlo el día que el proyecto tiene más de un archivo que no quieres perder. No hace falta esperar a "tenerlo bonito".

No subas secretos: .env, claves, contraseñas, archivos de servicio de AWS. Si ya ocurrió, el síntoma de abajo es urgente, no un arreglo estético.

Básico

Una vez en la máquina, si git --version falla, instala Git desde git-scm.com y abre una terminal nueva.

Dentro de la carpeta del proyecto:

git init
git status
git add index.html app.js estilos.css package.json package-lock.json .gitignore
git commit -m "Página de notas con alta y borrado"
git log --oneline

.gitignore antes del primer commit:

node_modules/
.env
dist/

Si node_modules ya se coló, no lo borres del disco. Quítalo del próximo commit:

echo node_modules/ >> .gitignore
git rm -r --cached node_modules
git commit -m "Deja de versionar node_modules"

Comandos que se usan cada día:

git status
git diff
git add -p
git commit -m "Valida el correo antes de guardar"

git add -p enseña cada trozo y pregunta. Es mejor que git add . cuando hay cambios mezclados que no quieres en el mismo commit. git diff muestra lo que aún no está en stage. git diff --staged muestra lo que sí entrará.

Identidad, solo en este repositorio, si Git se niega a commitear por falta de nombre:

git config user.name "Ada Lovelace"
git config user.email "ada@example.com"

Sin --global no toca otros proyectos. Esta biblioteca no cambia la configuración global.

Comprueba: git log --oneline muestra tu commit y git status dice que no hay nada pendiente.

Intermedio

Ramas y una copia en GitHub. Crea el repositorio vacío en GitHub (sin README, para no divergir) y enlázalo. Sustituye la URL por la tuya. HTTPS o SSH: si nunca configuraste una clave SSH, HTTPS con el gestor de credenciales de GitHub es el camino con menos piezas.

git switch -c arregla-formulario
git commit -m "Impide enviar el título vacío"
git push -u origin arregla-formulario

En GitHub, abre un pull request hacia main. Aunque trabajes solo, el PR es el checkpoint: lees el diff completo antes de fusionar. Fusiónalo con el botón de GitHub o en local:

git switch main
git pull
git merge arregla-formulario
git push

Traer cambios de otra persona, o los tuyos desde otro ordenador:

git pull

git pull es git fetch más git merge. Si prefieres ver qué llegó antes de mezclar: git fetch y luego git log HEAD..origin/main --oneline.

Deshacer con red de seguridad:

SituaciónComando
El archivo está modificado y quieres la versión del último commitgit restore archivo.js
Lo añadiste con git add y quieres sacarlo del stage, sin perder el cambiogit restore --staged archivo.js
El commit ya está hecho y no se ha empujado, y quieres añadir un archivo olvidadogit add archivo.js y git commit --amend --no-edit
El commit ya está en GitHubNo hagas amend. Un commit nuevo que corrige.

--amend reescribe el último commit. Si ya habías empujado ese commit, el siguiente push exigiría forzar la rama y pisar el historial remoto. No fuerces main.

Ver qué había en un commit viejo:

git show abc1234
git switch --detach abc1234

--detach mira ese commit sin mover la rama. Para volver: git switch main. No commitees en detached HEAD; si lo haces, crea una rama ahí mismo (git switch -c rescate) antes de irte.

Avanzado

Historial que ya está publicado y un error que no se borra "deshaciendo la pantalla".

Revertir un commit que ya está en main, sin reescribir:

git revert abc1234
git push

Eso crea un commit nuevo que deshace ese cambio. El historial de los demás sigue siendo válido.

Guardar trabajo a medias sin commitear basura:

git stash push -m "a medias el login"
git switch main
git stash pop

Si pop entra en conflicto, los archivos quedan marcados como en un merge. Resuélvelo igual que el síntoma de conflicto y borra el stash solo cuando git status esté limpio (git stash drop si pop ya lo aplicó a medias; comprueba git stash list).

Un secreto que llegó a GitHub hay que darlo por filtrado aunque borres el archivo en un commit posterior: sigue en el historial y en los clones ajenos. Rota la clave (en el proveedor: AWS, base de datos, GitHub) antes de limpiar el Git. Luego saca el archivo del último commit y añade la regla al .gitignore. Reescribir historia pública (git filter-repo, no cubierto como receta de un solo comando porque es fácil de equivocar) es el segundo paso, y exige avisar a quien haya clonado. La regla de oro está en 20-seguridad-minima.md.

Archivos grandes: Git no es un disco de vídeos ni de node_modules. Si un PDF o un zip pesado entró, el repositorio queda lento para siempre aunque lo borres después. Sácalo en el siguiente commit y, si aún no habías empujado, es el único momento razonable para rehacer el commit local.

Errores frecuentes

Perdiste cambios que no habías commiteado

Causa habitual: git restore, git checkout -- archivo o git reset --hard sobre un archivo que nunca estuvo en un commit. Git no puede devolver lo que no guardó.

Arreglo posible, sin garantía: el editor (Cursor, VS Code) tiene historial local del archivo (Timeline / Línea de tiempo, o Ctrl+Z si la pestaña sigue abierta). git stash list por si lo guardaste. git fsck --lost-found solo recupera commits, no cambios nunca añadidos. Si no está en ninguno, no hay comando que lo traiga de vuelta. A partir de aquí, commitea en cuanto el trozo funcione, aunque el mensaje sea wip: lista que ya añade.

Conflicto de merge

Causa habitual: las dos ramas editaron las mismas líneas. Git escribe marcas dentro del archivo:

<<<<<<< HEAD
const limite = 80;
=======
const limite = 120;
>>>>>>> arregla-formulario

Arreglo: abre el archivo, deja el código que debe quedar (una de las dos versiones, o una mezcla), borra las tres marcas (<<<<<<<, =======, >>>>>>>). Busca en el proyecto si quedó alguna marca: una que se escape rompe el programa. Después:

git add archivo.js
git commit

No hace falta un mensaje elaborado: Git propone "Merge...". Si el conflicto es solo package-lock.json, no lo unas a mano; sigue 04-npm.md.

Hiciste el commit en la rama equivocada

Causa habitual: estabas en main y el commit todavía no se ha empujado.

Arreglo si no está empujado:

git switch -c arregla-formulario
git switch main
git reset --hard HEAD~1

Eso mueve el commit a la rama nueva (al cambiar de rama te lo llevas, porque el commit es tuyo y main lo tenía) y luego deja main un commit atrás. --hard borra cambios no commiteados. Haz git status antes y confirma que está limpio.

Si ya empujaste a main, no reescribas. Crea la rama donde estás y revierte en main con git revert si ese commit no debía publicarse.

push rejected o non-fast-forward

Causa habitual: en GitHub hay commits que tú no tienes (otro ordenador, o el botón de editar en la web).

Arreglo:

git fetch
git pull
git push

Si pull abre un conflicto, es el síntoma anterior. No uses git push --force en main. En una rama tuya que nadie más usa, --force-with-lease es el único force aceptable, y solo si sabes que estás reescribiendo a propósito (después de un amend que ya habías empujado por error).

Subiste un secreto en un commit

Causa habitual: un .env o un JSON de claves añadido con git add ..

Arreglo, en este orden, el mismo día:

  1. Revoca la clave en el servicio que la emitió y crea otra. La antigua quedó expuesta en cuanto se empujó, y también si el repositorio era privado y hubo un clon.
  2. Quita el archivo del árbol y añádelo al .gitignore. Commit nuevo.
  3. Confirma que la app usa la clave nueva desde un .env que no está en Git.
  4. Si el repositorio es público, asume que la clave vieja ya se copió. Rotarla es el arreglo; borrar el commit no alcanza.

Cómo comprobar

  1. git status limpio después de cada decisión de "esto ya está".
  2. Un compañero, u otra carpeta tuya, hace git clone y npm ci y el proyecto arranca sin pedirte archivos por chat.
  3. Una rama con un commit pequeño se fusiona por pull request y main queda con ese cambio.
  4. git log --oneline se lee como una lista de pasos, no como un único commit "cambios".

Si esto no alcanza

Documentación de Git: git restore, git switch, git revert, git merge conflicts.

De GitHub: about pull requests, cloning a repository, removing sensitive data from a repository si llegaste al secreto ya empujado.

Checkpoint — trabajo colaborativo (45 a 60 minutos)

Con el proyecto ya en un repositorio local:

  • .gitignore que excluye node_modules y .env.
  • Repositorio en GitHub y al menos dos commits en main con mensajes que dicen qué se logró.
  • Una rama, un cambio pequeño (un texto, una validación), un pull request y la fusión.
  • git pull en una segunda carpeta clonada, para ver el cambio llegar.

Hecho cuando el clon tiene el mismo código que das por bueno, sin copiar la carpeta a mano.

React

React parte la pantalla en componentes: funciones que devuelven el HTML de un trozo y se vuelven a ejecutar cuando cambian sus datos (el estado). El mapa lo coloca junto a Tailwind y permite saltarlo hasta después del backend. Antes de esta ficha tienen que estar firmes el HTML, el CSS y el JavaScript de las fichas 01 a 03. React no sustituye esas tres: las organiza.

El empaquetador de estos ejemplos es Vite. Crear el proyecto:

npm create vite@latest notas-ui -- --template react
cd notas-ui
npm install
npm install tailwindcss @tailwindcss/vite
npm run dev

La conexión de Tailwind está en 02-css-y-tailwind.md. Entra a la URL que imprime el comando (normalmente http://localhost:5173).

Cuándo usarlo y cuándo no

Úsalo cuando haya varias pantallas o una pantalla cuyo HTML cambia según datos (listas, formularios, sesión). Para una página de un solo bloque estático, React sobra: el checkpoint de HTML es más claro sin él.

No hace falta React para llamar a una API. fetch ya lo hace. React entra cuando quieres que el resultado de esa llamada pinte la pantalla sin que tú toques el DOM a mano.

Básico

Un componente, un estado, una lista. src/App.jsx:

import { useState } from "react";

export default function App() {
  const [titulo, setTitulo] = useState("");
  const [notas, setNotas] = useState([]);

  function agregar(event) {
    event.preventDefault();
    const texto = titulo.trim();
    if (!texto) return;
    setNotas((prev) => [...prev, { id: crypto.randomUUID(), texto }]);
    setTitulo("");
  }

  function borrar(id) {
    setNotas((prev) => prev.filter((n) => n.id !== id));
  }

  return (
    <main className="mx-auto max-w-xl p-6">
      <h1 className="text-xl font-semibold">Notas</h1>
      <form onSubmit={agregar} className="mt-4 flex gap-2">
        <label className="sr-only" htmlFor="titulo">Título</label>
        <input
          id="titulo"
          value={titulo}
          onChange={(e) => setTitulo(e.target.value)}
          className="w-full rounded border border-stone-300 px-3 py-2"
        />
        <button type="submit" className="rounded bg-stone-900 px-3 py-2 text-white">
          Guardar
        </button>
      </form>
      <ul className="mt-6 grid gap-2">
        {notas.map((nota) => (
          <li key={nota.id} className="flex items-center justify-between gap-3 rounded border border-stone-300 p-3">
            <span>{nota.texto}</span>
            <button type="button" onClick={() => borrar(nota.id)}>Borrar</button>
          </li>
        ))}
      </ul>
    </main>
  );
}

Reglas que evitan los síntomas de abajo:

  • El HTML de React se llama JSX y va en return. Escribes className, no class, y cierras todas las etiquetas (<input />, <li>...</li>).
  • El estado se cambia con la función (setNotas), no con notas.push. Un push modifica el mismo array y React puede no repintar.
  • La forma setNotas((prev) => ...) usa el valor más reciente. Hace falta cuando el nuevo valor depende del anterior y hay varios clics seguidos.
  • key={nota.id} identifica la fila. El índice del array sirve solo si la lista no se reordena ni se borra por el medio.
  • sr-only de Tailwind deja el label disponible para el lector de pantalla y lo oculta en la vista. Si no usas Tailwind, un <label> visible es mejor que uno escondido a mano.

Comprueba: npm run dev, añade dos notas, borra la primera. Recargar las pierde: siguen en memoria. Igual que en el JavaScript básico.

Intermedio

Datos que vienen del servidor, pantalla de carga y pantalla de error. El servidor puede ser el de 09-api-rest.md. Mientras no exista, apunta el fetch a una lista fija solo para ver el estado de carga, y cámbialo en cuanto la API responda.

import { useEffect, useState } from "react";

export default function ListaNotas() {
  const [notas, setNotas] = useState([]);
  const [estado, setEstado] = useState("cargando");

  useEffect(() => {
    const controlador = new AbortController();
    fetch("/api/notas", { signal: controlador.signal })
      .then((respuesta) => {
        if (!respuesta.ok) throw new Error("HTTP " + respuesta.status);
        return respuesta.json();
      })
      .then((datos) => {
        setNotas(datos);
        setEstado("listo");
      })
      .catch((error) => {
        if (error.name === "AbortError") return;
        setEstado("error");
      });
    return () => controlador.abort();
  }, []);

  if (estado === "cargando") return <p>Cargando…</p>;
  if (estado === "error") return <p>No se pudieron cargar las notas.</p>;
  if (notas.length === 0) return <p>No hay notas todavía.</p>;

  return (
    <ul>
      {notas.map((nota) => (
        <li key={nota.id}>{nota.texto}</li>
      ))}
    </ul>
  );
}

El array vacío [] al final de useEffect significa "una vez, al aparecer el componente". Sin ese array, el efecto corre después de cada pintado y, si dentro hay un setNotas, el pintado se repite sin fin.

AbortController cancela la petición si el usuario se va de la pantalla antes de que responda. Sin eso, la respuesta llega y llama a setNotas en un componente que ya no está, y React avisa.

En desarrollo, Vite puede proxyar /api al Node del puerto 3000 para no pelear con CORS. En vite.config.js:

export default defineConfig({
  plugins: [react(), tailwindcss()],
  server: { proxy: { "/api": "http://localhost:3000" } },
});

Ese proxy no existe en el build de producción. En producción el navegador y la API comparten origen gracias a Nginx, como en 15-despliegue.md, o la API manda las cabeceras CORS.

Varias pantallas sin meter un router todavía: un estado vista con valores "lista" y "detalle" basta para el checkpoint. React Router entra cuando haya URLs que una persona quiera guardar o compartir (/notas/12). Paquete: react-router. Rutas mínimas:

import { BrowserRouter, Route, Routes, Link } from "react-router";

export default function App() {
  return (
    <BrowserRouter>
      <nav><Link to="/">Lista</Link></nav>
      <Routes>
        <Route path="/" element={<ListaNotas />} />
        <Route path="/nueva" element={<NuevaNota />} />
      </Routes>
    </BrowserRouter>
  );
}

El nombre del paquete y el del import cambian según la versión mayor. Si el import falla, abre node_modules/react-router/package.json y mira el campo que la documentación de esa versión indica, o busca react router installation para el número que instalaste. No mezcles tutoriales de la versión 6 con la 7.

Avanzado

Lo que se rompe cuando el componente se usa en serio.

Subir el estado al padre solo si dos hermanos lo necesitan. Si solo lo usa un formulario, déjalo dentro del formulario. Un App.jsx con veinte useState es la señal de partir componentes, no de instalar un gestor de estado global. Para esta app no hace falta Redux ni Zustand.

Formulario de edición: copia el dato al estado local al abrir, guarda contra el servidor, y vuelve a pedir la lista. No edites el objeto de la lista "en caliente" si el usuario puede cancelar.

function guardarCambio(id, texto) {
  setNotas((prev) => prev.map((n) => (n.id === id ? { ...n, texto } : n)));
}

El ...n copia el resto de campos. n.texto = texto muta el objeto que React ya tenía y a veces no repinta, a veces repinta a medias.

Listas largas: no pagines en el navegador trayendo 10 000 filas. Pide ?limit=20&cursor= a la API, como en 09-api-rest.md.

npm run build
npm run preview

dist/ es HTML, CSS y JS estáticos. El servidor web los sirve; Node no tiene por qué servirlos si ya tienes Nginx. Errores frecuentes

Pantalla en blanco solo con React

Causa habitual: un error al renderizar. En desarrollo, React muestra una caja roja; si el error ocurre antes de montar, solo está en la consola. También pasa si main.jsx apunta a un div#root que no existe en index.html.

Arreglo: abre la consola y lee la primera línea tuya, no la de react-dom. Comprueba que index.html tiene <div id="root"></div> y que main.jsx hace createRoot(document.getElementById("root")).render(<App />). Si la caja roja dice que un componente devolvió undefined, falta el return del JSX.

El estado no cambia en pantalla

Causa habitual: mutaste el array o el objeto (notas.push, nota.texto = ...) y llamaste a setNotas(notas) con la misma referencia. React compara por identidad y no ve un cambio.

Arreglo: crea un array nuevo, como en setNotas((prev) => [...prev, nota]) o filter / map. Comprueba con un console.log dentro del componente: si el log muestra el dato nuevo y la pantalla no, el valor pintado no es ese estado (estás leyendo otra variable).

Maximum update depth exceeded o el efecto se dispara sin parar

Causa habitual: useEffect sin el array de dependencias, o con una dependencia que es un objeto creado en cada pintado (useEffect(..., [ { id } ]) crea un objeto nuevo siempre). Dentro del efecto hay un setState, que vuelve a pintar, que vuelve a lanzar el efecto.

Arreglo: dependencia [] si de verdad es "al montar". Si depende de un id, pasa el id primitivo ([id]), no un objeto. No hagas setNotas incondicional dentro de un efecto que depende de notas.

Aviso de key en una lista

Causa habitual: un .map que devuelve elementos sin key, o con key={index} y luego reordenas o borras.

Arreglo: key={nota.id} con un id estable. No uses Math.random() como key: cambia en cada pintado y el input pierde el foco. El aviso está en la consola y nombra el componente.

Un input no deja escribir, o React avisa de controlado y no controlado

Causa habitual: value={titulo} sin onChange, entonces React lo deja fijo en el valor inicial. O value={nota.titulo} cuando titulo a veces es undefined (pasa de no controlado a controlado).

Arreglo: pareja value y onChange, como en el básico. Si el dato puede faltar, usa value={titulo ?? ""}. Un input que el navegador maneja solo, sin estado, se escribe con defaultValue, no con value.

Cómo comprobar

  1. npm run dev muestra la lista, el alta y el borrado.
  2. Un título con <b> se ve literal, no en negrita.
  3. La consola no tiene el aviso de key ni el de máximo de actualizaciones.
  4. Recargar con la API apagada muestra el párrafo de error, no una página en blanco.
  5. npm run build termina y npm run preview abre esa build. Eso es lo que se despliega, no el dev.

Si esto no alcanza

En react.dev: react useState, react useEffect, react rendering lists, react forms, react you might not need an effect.

Si el error nombra un hook, busca esa frase entre comillas junto con react.dev.

Node.js

Node ejecuta JavaScript fuera del navegador. En esta biblioteca hace dos trabajos: programas de terminal (el checkpoint CLI) y el servidor HTTP de la API. El lenguaje es el de 03-javascript.md; cambian las herramientas (fs, process, red) y desaparece el document.

Comprueba la instalación:

node -v
npm -v

Hace falta la versión LTS (20 o 22). Si el número no sale, instálala desde nodejs.org y abre otra terminal.

Cuándo usarlo y cuándo no

Úsalo para scripts (renombrar archivos, transformar un CSV) y para la API. El roadmap recomienda Node porque ya sabes JavaScript. Python, Java, PHP o C# cubren el mismo hueco; no hay un segundo tutorial aquí.

No uses Node para servir la página estática del primer checkpoint: con abrir el HTML basta. Tampoco lo uses para cálculos pesados de horas si un SQL bien escrito lo resuelve en 08-postgresql.md.

Básico

Un script que lee un CSV y escribe un resumen. src/cli.js:

import { readFile } from "node:fs/promises";

const ruta = process.argv[2];
if (!ruta) {
  console.error("Uso: node src/cli.js notas.csv");
  process.exitCode = 1;
  process.exit();
}

const texto = await readFile(ruta, "utf8");
const lineas = texto.split(/\r?\n/).filter(Boolean);
const cabecera = lineas.shift();
if (cabecera?.trim() !== "titulo") {
  console.error("La primera línea tiene que ser: titulo");
  process.exitCode = 1;
  process.exit();
}

let vacias = 0;
for (const linea of lineas) {
  if (linea.trim() === "") vacias += 1;
}
console.log(`Filas: ${lineas.length}`);
console.log(`Vacías: ${vacias}`);

package.json necesita "type": "module" para poder usar import. Si no está, Node dice que import no es válido fuera de un módulo: es el síntoma ESM de abajo, no un fallo del CSV.

node src/cli.js notas.csv

process.argv[0] es node, [1] es el archivo, [2] es tu primer argumento. process.exitCode = 1 marca fallo sin cortar a medias los console.log pendientes; process.exit() sí corta, y aquí hace falta porque si no el script seguiría.

En Windows el CSV puede venir con \r\n. El split(/\r?\n/) cubre los dos. Si partes solo por \n, la cabecera queda como "titulo\r" y la comparación falla.

Servidor mínimo, solo para ver un puerto vivo. La API de verdad está en 09-api-rest.md; aquí basta saber que Node escucha.

import { createServer } from "node:http";

const puerto = Number(process.env.PORT) || 3000;
const servidor = createServer((req, res) => {
  res.writeHead(200, { "content-type": "text/plain; charset=utf-8" });
  res.end("ok");
});
servidor.listen(puerto, () => {
  console.log(`http://localhost:${puerto}`);
});
node src/server.js

Déjalo corriendo y, en otra terminal, curl http://localhost:3000. Tiene que imprimir ok. Para parar: Ctrl+C en la terminal del servidor.

Intermedio

Variables de entorno y un proceso que no mezcla configuración con código.

Archivo .env en la raíz, nunca en Git:

PORT=3000
DATABASE_URL=postgres://notas:notas@localhost:5432/notas

Node 20.6+ y 22 leen ese archivo sin paquete:

node --env-file=.env src/server.js

En el código solo se lee process.env. No hay valores de producción escritos en el archivo .js.

const puerto = Number(process.env.PORT);
if (!puerto) {
  console.error("Falta PORT en el entorno");
  process.exit(1);
}

Si PORT no está, prefiere abortar a escuchar en un puerto sorpresa. El || 3000 del básico es cómodo en un ejercicio y peligroso en un servidor, porque esconde una configuración ausente.

Script de package.json:

{
  "type": "module",
  "scripts": {
    "dev": "node --watch --env-file=.env src/server.js",
    "start": "node --env-file=.env src/server.js",
    "cli": "node --env-file=.env src/cli.js"
  }
}

--watch reinicia al guardar. Es el modo de trabajo. start es el que usará systemd en 15-despliegue.md, sin watch.

Errores que no se tragan:

process.on("unhandledRejection", (error) => {
  console.error(error);
  process.exit(1);
});

Un await olvidado dentro de un setTimeout, o una promesa sin catch, puede tumbar el proceso más tarde con un mensaje pobre. Este escuchador imprime la causa y sale. Quien debe volver a levantarlo es Monit o systemd, no un catch vacío. Ver 16-monitoreo.md.

Estructura que aguanta el resto de la biblioteca:

src/cli.js        scripts de terminal
src/server.js     arranque HTTP
src/db.js         conexión a PostgreSQL
.env              secretos locales, en .gitignore

Un archivo por tema. Cuando server.js pase de ~150 líneas, se parte por rutas (src/notas.js), no por "capas" con nombres vacíos.

Avanzado

Lo que se rompe cuando el proceso vive en un servidor y hay más de una petición a la vez.

Node hace una sola cosa a la vez en el hilo de JavaScript. Una función síncrona pesada (readFileSync de un archivo grande, un JSON.parse enorme, un bucle de millones) congela todas las peticiones, también las que "ya habían llegado". Lectura de archivos de usuario: fs/promises. CPU de verdad (imagen, zip, informe): otro proceso, o un trabajo en cola. No lo resuelvas poniendo más async alrededor de un bucle síncrono: async no mueve ese trabajo a otro hilo.

Cierre ordenado, para que un reinicio no corte una respuesta a medias:

for (const senal of ["SIGINT", "SIGTERM"]) {
  process.on(senal, () => {
    servidor.close(() => process.exit(0));
    setTimeout(() => process.exit(1), 10_000).unref();
  });
}

systemd manda SIGTERM al parar el servicio. Sin este bloque, las peticiones en curso se cortan. El temporizador evita quedarse colgado si alguna conexión no termina.

No loguees el cuerpo completo de un login ni el valor de Authorization. Loguea método, ruta, código y milisegundos:

servidor.on("request", (req, res) => {
  const inicio = Date.now();
  res.on("finish", () => {
    console.log(`${req.method} ${req.url} ${res.statusCode} ${Date.now() - inicio}ms`);
  });
});

Eso, redirigido a journald en 13-linux.md, es el log que vas a leer a las once de la noche.

El proceso de producción se arranca con node src/server.js, no con npm run dev ni con --watch. El usuario del servicio no es root. Esas dos decisiones están aplicadas en el despliegue, pero se deciden aquí: si el código solo funciona corriendo como administrador o vigilando archivos, no está listo.

Errores frecuentes

EADDRINUSE, el puerto está ocupado

Causa habitual: ya hay un Node con ese puerto, a menudo un --watch que no mataste, o dos proyectos en el 3000.

Arreglo en Windows (PowerShell):

netstat -ano | findstr :3000
taskkill /PID EL_NUMERO /F

El número de la última columna es el PID. Mata ese PID, no el primero que veas en la lista si hay varias líneas: busca el que está en LISTENING.

En Linux:

ss -ltnp | grep :3000
kill EL_PID

Si el proceso es el servicio systemd, no lo mates a mano: sudo systemctl restart notas. Ver 13-linux.md.

require is not defined, o el import falla

Causa habitual: el archivo usa import y package.json no tiene "type": "module". Al revés: un ejemplo viejo con require dentro de un proyecto que sí es módulo.

Arreglo: elige uno. En esta biblioteca todo es ESM.

{ "type": "module" }
import express from "express";

Los imports de archivos tuyos llevan extensión: import { pool } from "./db.js";. Node no rellena .js como a veces hace el navegador empaquetado por Vite. Un directorio importado tiene que tener index.js y tú igual escribes la ruta completa si no es un paquete.

__dirname no existe en ESM. La ruta del archivo actual es:

import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";

const aqui = dirname(fileURLToPath(import.meta.url));
const env = join(aqui, "..", ".env");

process.env.ALGO es undefined

Causa habitual, en este orden:

  1. Arrancaste con node src/server.js y olvidaste --env-file=.env.
  2. El .env está en otra carpeta. --env-file es relativo al directorio desde el que lanzas el comando, no al archivo .js.
  3. El nombre no coincide: DATABASE_URL en el archivo y process.env.DATABASE en el código. Sobran espacios: PORT = 3000 a veces se lee mal; escribe PORT=3000.
  4. En el servidor el .env no existe y las variables viven en systemd. Estás mirando el archivo local. Ver 15-despliegue.md.

Arreglo: imprime solo los nombres, nunca los valores si pueden ser secretos.

console.log("PORT definido:", Boolean(process.env.PORT));

Si es false, el proceso no vio el entorno. Corrige el comando de arranque antes de tocar el código.

El proceso muere y no queda log

Causa habitual: se cerró la terminal, o el error fue a un console.error que nadie redirige, o un unhandledRejection en una versión que solo avisa. También pasa si el servicio de systemd tiene StandardOutput=null o estás mirando el archivo de log equivocado.

Arreglo en local: arranca en primer plano (npm run dev) y reproduce el fallo. El mensaje aparece en esa terminal. Si solo muere "en el servidor", el log es journalctl -u notas -n 100 --no-pager, no tu terminal de SSH de ayer. Deja puesto el escuchador de unhandledRejection del nivel intermedio para que la razón quede escrita antes de salir.

Cómo comprobar

  1. node src/cli.js notas.csv imprime el recuento y, si le pasas un archivo sin la cabecera, el código de salida no es 0 (echo $LASTEXITCODE en PowerShell, echo $? en bash justo después).
  2. curl http://localhost:3000 imprime ok mientras el proceso está en primer plano, y deja de conectar cuando haces Ctrl+C.
  3. Renombra temporalmente .env. El proceso tiene que negarse a arrancar si falta PORT, no escuchar en silencio.
  4. git status no lista .env.

Si esto no alcanza

Documentación de Node: nodejs fs promises, nodejs process argv, nodejs http server, nodejs --env-file, nodejs esm import.

El texto de EADDRINUSE se busca literal si el mensaje incluye otra causa (permiso, puerto por debajo de 1024).

PostgreSQL

PostgreSQL guarda las filas y las sigue teniendo cuando el proceso de Node se apaga. Esta ficha cubre el checkpoint de CRUD: crear, leer, actualizar y borrar. La forma HTTP de ese CRUD está en 09-api-rest.md. Aquí se comprueba con psql y con un script, para no mezclar un fallo de SQL con un fallo de rutas.

También se puede usar MySQL o SQLite para lo mismo. El mapa pide PostgreSQL; los ejemplos son de PostgreSQL.

Cuándo usarlo y cuándo no

Úsalo cuando el dato tenga que estar mañana, o cuando lo vea otra persona. Para un borrador de una sola pestaña basta localStorage, y ya sabes su límite desde 03-javascript.md.

No guardes archivos grandes (fotos, PDF) dentro de una fila. La fila guarda la ruta; el archivo va a disco o a S3, en 14-aws-basico.md.

Básico

Instalación local, la que vas a usar para practicar:

  • Windows: instalador de postgresql.org. Durante el asistente anota la contraseña del usuario postgres y el puerto 5432. Al terminar existe "SQL Shell (psql)".
  • Linux (servidor o WSL): sudo apt update && sudo apt install postgresql y luego el bloque de usuario de abajo.

Crea un usuario y una base solo para esta app. No uses el usuario postgres desde Node.

En Linux, como el usuario del sistema postgres:

sudo -u postgres psql

En Windows, abre psql con el usuario postgres y la contraseña del instalador. El SQL es el mismo:

CREATE USER notas WITH PASSWORD 'notas';
CREATE DATABASE notas OWNER notas;
\q

Conéctate a esa base:

psql "postgres://notas:notas@localhost:5432/notas"

Si la contraseña tiene caracteres como @ o #, hay que codificarlos en la URL (@ pasa a %40). Por eso, en local, una contraseña simple de práctica evita un rato de confusión. En producción la contraseña es larga y va en un archivo de entorno, no en el comando que queda en el historial: usa la variable PGPASSWORD solo en la sesión, o un archivo .pgpass.

Tabla mínima:

CREATE TABLE notes (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  text text NOT NULL CHECK (char_length(text) BETWEEN 1 AND 2000),
  created_at timestamptz NOT NULL DEFAULT now()
);

CRUD desde psql, para ver que la base cumple antes de escribir Node:

INSERT INTO notes (text) VALUES ('Revisar el formulario') RETURNING id, text;
SELECT id, text, created_at FROM notes ORDER BY id;
UPDATE notes SET text = 'Revisar el formulario HTML' WHERE id = 1 RETURNING id, text;
DELETE FROM notes WHERE id = 1 RETURNING id;

RETURNING te devuelve la fila afectada. Sin WHERE, un UPDATE o un DELETE tocan toda la tabla. Antes de ejecutarlos, escribe el SELECT con el mismo WHERE y mira cuántas filas salen.

El dato ya no es una nota suelta: tiene dueño, y el esquema cambia con archivos, no a mano en producción.

db/001_init.sql:

CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,
  password_hash text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE notes (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users (id),
  text text NOT NULL CHECK (char_length(text) BETWEEN 1 AND 2000),

CREATE INDEX notes_user_created_idx ON notes (user_id, created_at DESC);

Si ya creaste notes en el básico, no ejecutes este archivo encima: los nombres chocan. En local puedes DROP TABLE notes; y empezar. En una base con datos que importan, escribes 002_....sql que altera, no un init nuevo.

db/002_note_status.sql:

ALTER TABLE notes ADD COLUMN status text NOT NULL DEFAULT 'abierta'
  CHECK (status IN ('abierta', 'cerrada'));

Una tabla de control evita aplicar dos veces la misma migración:

CREATE TABLE schema_migrations (
  filename text PRIMARY KEY,
  applied_at timestamptz NOT NULL DEFAULT now()
);

src/migrate.js aplica, en orden alfabético, los .sql que aún no están en esa tabla. Cada archivo va en una transacción: o entra entero, o no entra.

import { readdir, readFile } from "node:fs/promises";
import { pool } from "./db.js";

await pool.query(`
  CREATE TABLE IF NOT EXISTS schema_migrations (
    filename text PRIMARY KEY,
    applied_at timestamptz NOT NULL DEFAULT now()
  )
`);

const archivos = (await readdir("db")).filter((n) => n.endsWith(".sql")).sort();
for (const filename of archivos) {
  const ya = await pool.query(
    "SELECT 1 FROM schema_migrations WHERE filename = $1",
    [filename],
  );
  if (ya.rowCount) continue;

  const sql = await readFile(new URL(`../db/${filename}`, import.meta.url), "utf8");
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query(sql);
    await client.query(
      "INSERT INTO schema_migrations (filename) VALUES ($1)",
      [filename],
    );
    await client.query("COMMIT");
    console.log("aplicada", filename);
  } catch (error) {
    await client.query("ROLLBACK");
    console.error("falló", filename);
    console.error(error.message);
    process.exitCode = 1;
    break;
  } finally {
    client.release();
  }
}
await pool.end();

La ruta del readFile asume que el comando se lanza en la raíz del proyecto (node --env-file=.env src/migrate.js). readdir("db") es relativo a esa raíz.

Consulta de la app, siempre con el dueño:

SELECT id, text, status, created_at
FROM notes
WHERE user_id = $1
ORDER BY created_at DESC
LIMIT 20;

Sin user_id = $1, un usuario lee las notas de los demás en cuanto adivina un id. El id predecible (1, 2, 3) no es un secreto. El filtro por dueño sí es la autorización, junto con 10-jwt.md.

Transacción cuando dos escrituras tienen que ir juntas (crear usuario y su primera nota, o descontar y apuntar el movimiento):

const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("INSERT INTO users (email, password_hash) VALUES ($1, $2)", [email, hash]);
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}

pool.query suelta la conexión después de cada llamada. Dos pool.query seguidos pueden caer en conexiones distintas y el BEGIN no cubre al segundo. Por eso la transacción usa un client reservado.

Avanzado

Lo que se rompe con datos de verdad.

Índice para la consulta que ya tienes, no para todas las columnas. El de (user_id, created_at DESC) sirve al listado del intermedio. Un índice de más ralentiza cada INSERT. Comprueba con:

EXPLAIN ANALYZE
SELECT id, text FROM notes WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;

Quieres ver Index Scan o Bitmap sobre ese índice cuando hay muchas filas. Con 10 filas, Postgres puede preferir un Seq Scan y estar en lo cierto: leer la tabla entera es más barato. No añadas índices para ganar un EXPLAIN de un ejemplo diminuto.

NULL no es "vacío". WHERE email = NULL no devuelve nada. Se escribe WHERE email IS NULL. Una columna NOT NULL te ahorra esa rama.

Borrado: DELETE físico en una nota que el usuario tira a la papelera. Un status = 'borrada' si necesitas deshacer. Elige uno y no filtres "a veces". Las consultas del listado tienen que excluir las borradas siempre:

WHERE user_id = $1 AND status <> 'borrada'

Copia de seguridad, en la máquina donde está la base, con un archivo que no se versiona:

pg_dump "postgres://notas@localhost:5432/notas" --format=custom --file=notas.dump
pg_restore --dbname=notas_prueba notas.dump

pg_dump sin probar el pg_restore no es una copia: es un archivo que crees que funciona. Restaura en otra base (notas_prueba) una vez antes de necesitarlo. En el servidor, ese comando va a un cron y el archivo sale del mismo disco de la base (S3, en la ficha de AWS). Un disco lleno se lleva la base y la copia a la vez.

Conexiones: el Pool de pg abre varias. El valor por defecto basta para una app pequeña. Si Postgres dice too many connections, no subas el límite del servidor como primer arreglo: mira cuántos procesos Node hay (un --watch más un test más el servidor) y si cada uno crea su pool. Un solo proceso, un solo pool.

Errores frecuentes

ECONNREFUSED en el puerto 5432, o connection refused

Causa habitual: PostgreSQL no está arrancado, o DATABASE_URL apunta a otro host.

Arreglo: en Windows, el servicio se llama parecido a postgresql-x64-16. Ábrelo desde "Servicios" o con Get-Service *postgres*. En Linux, sudo systemctl status postgresql. Luego psql con la misma URL que usa Node. Si psql entra y Node no, la URL del .env no es la que crees: el síntoma de entorno está en 07-nodejs.md.

password authentication failed

Causa habitual: la contraseña del .env no es la del CREATE USER, o estás entrando como otro usuario. postgres y notas no comparten contraseña.

Arreglo: entra como administrador (sudo -u postgres psql o el psql de Windows) y fija la contraseña otra vez:

ALTER USER notas PASSWORD 'notas';

Actualiza .env y reinicia Node. Un cambio de .env no entra en un proceso que ya estaba corriendo.

relation "notes" does not exist

Causa habitual: la tabla está en otra base, o no aplicaste la migración contra la base a la que Node se conecta. También, en PostgreSQL el nombre sin comillas se guarda en minúsculas: "Notes" y notes no son la misma.

Arreglo:

\conninfo
\dt

\conninfo dice a qué base entraste. \dt lista las tablas. Si notes no está, corre src/migrate.js con el mismo DATABASE_URL. Si estás en la base postgres por defecto, la URL no incluye /notas.

La migración falla a medias

Causa habitual: el archivo SQL tiene dos sentencias y la segunda falla (un tipo que no existe, una tabla ya creada). Sin transacción, la primera queda aplicada y la tabla de control no registra el archivo, así que el siguiente intento repite la primera y falla con already exists.

Arreglo: el migrate.js de arriba hace ROLLBACK si algo falla, así que no deja la primera sentencia puesta. Si ya te pasó con un script a mano, mira \dt y SELECT * FROM schema_migrations. Borra a mano, en local, lo que se quedó a medias o escribe un 003 que sea idempotente (ADD COLUMN IF NOT EXISTS solo cuando de verdad es seguro repetirlo). No marques la migración como aplicada si el \dt no coincide con lo que el archivo prometía.

duplicate key value violates unique constraint

Causa habitual: dos altas con el mismo email, o un INSERT que fija el id que ya existe. Es una respuesta de negocio, no un 500.

Arreglo en SQL de comprobación: SELECT id FROM users WHERE email = $1. En la API se traduce a 409, en 09-api-rest.md. No quites el UNIQUE para que el error desaparezca: el índice es lo que impide dos usuarios con el mismo correo cuando los dos clics llegan a la vez. El SELECT previo no basta, porque los dos pueden pasar el SELECT antes de que ninguno inserte.

La consulta tarda segundos

Causa habitual: un WHERE sobre una columna sin índice en una tabla grande, o un SELECT * que trae texto enorme que no ibas a mostrar. Menos veces, en este nivel: falta un índice y además estás filtrando en Node una tabla entera que ya pudiste filtrar en SQL.

Arreglo: EXPLAIN ANALYZE con los mismos parámetros. Si ves Seq Scan y la tabla tiene muchas filas, el WHERE no está cubierto por un índice. Crea el índice que coincide con el filtro (user_id, y el orden si hay ORDER BY). No indexes una columna "por si acaso" que ninguna consulta filtra. Confirma que el listado pide LIMIT.

Cómo comprobar

  1. psql con la URL de la app lista las tablas (\dt) y una fila de prueba.
  2. El script add y el script list ven esa fila.
  3. Un texto de 2001 caracteres lo rechaza el CHECK, no la pantalla.
  4. Aplicar migraciones dos veces seguidas no da error: la segunda dice que no hay nada nuevo.
  5. EXPLAIN del listado por usuario no recorre una tabla distinta de la que crees (mira el nombre en el plan).

Si esto no alcanza

Documentación de PostgreSQL: postgresql insert returning, postgresql where, postgresql explain, postgresql create index, postgresql pg_dump.

El mensaje de error, entre comillas, más postgresql, encuentra la página del código (42P01 es la relación que no existe, 23505 es la clave duplicada).

API REST

Una API REST es un acuerdo sobre HTTP: cada URL es un recurso, el método dice qué quieres hacerle y el código de estado dice qué pasó. El navegador de 06-react.md y un curl tienen que poder usar el mismo acuerdo. Si solo funciona desde la pantalla, no es una API: es un efecto secundario de React.

El servidor de esta ficha es Express sobre Node. Viene de 07-nodejs.md y habla con 08-postgresql.md.

Cuándo usarlo y cuándo no

Úsalo cuando otro programa (el frontend, un script, mañana un móvil) necesite los datos. No hace falta una API para la página estática ni para el script de terminal.

GraphQL cubre el mismo hueco con otro contrato. El mapa pide REST. No mantengas los dos "por aprender".

Avanzado

Lo que se rompe con clientes reales, reintentos y listas que crecen.

Idempotencia de un alta. Un cliente que no recibió la respuesta (se cayó la red) reintenta el POST y crea dos notas. Un Idempotency-Key guardado un rato corta el duplicado:

app.post("/api/notas", asyncRoute(async (req, res) => {
  const clave = req.get("Idempotency-Key");
  if (!clave || clave.length > 80) {
    res.status(400).json({ error: "Falta Idempotency-Key" });
    return;
  }
  const previa = await pool.query(
    "SELECT note_id FROM idempotency_keys WHERE key = $1",
    [clave],
  );
  if (previa.rows[0]) {
    const nota = await pool.query(
      "SELECT id, text, created_at FROM notes WHERE id = $1",
      [previa.rows[0].note_id],
    );
    res.status(200).json(nota.rows[0]);
    return;
  }
  // INSERT de la nota y de la clave, en la misma transacción del archivo de PostgreSQL.
}));

La tabla es (key text primary key, note_id bigint not null, created_at timestamptz default now()). Sin la transacción única, puedes guardar la nota y no la clave. Es el mismo patrón de BEGIN de 08-postgresql.md. Para el checkpoint no es obligatorio. Sí lo es no devolver 500 cuando el segundo POST choca: o devuelves la nota ya creada, o un 409 claro.

Validación en el servidor aunque React ya la haya hecho. El HTML y el disabled del botón se saltan con curl. La fuente de la verdad es esta ficha, no el formulario.

Rutas fijas antes que rutas con parámetro si alguna vez se parecen (/api/notas/resumen tiene que declararse antes de /api/notas/:id, o resumen se interpreta como id).

Límite de tamaño y de ritmo. express.json({ limit: "32kb" }) cubre el cuerpo. Un límite de cuántas peticiones por minuto aceptas por IP evita que un bucle de un bug te tumbe Postgres. En una app pequeña puedes contarlo en memoria; cuando haya más de un proceso Node, el contador vive en Redis, en 11-redis.md. No hace falta un paquete para entender el mecanismo: una clave rl:ip, INCR, y EXPIRE la primera vez.

Versión de la API en la ruta (/api/... ya es tu versión 1). El día que un cambio rompa a los clientes viejos, publicas /api/v2 y dejas la anterior hasta que no queden llamadas en el log. No cambies el significado de un campo en silencio.

Errores frecuentes

CORS, No 'Access-Control-Allow-Origin'

Causa habitual: la página está en un origen (esquema + host + puerto) y la API en otro. http://localhost:5173 y http://localhost:3000 son orígenes distintos. El navegador hace la petición, ve que la respuesta no autoriza al origen de la página y esconde el cuerpo. curl no aplica CORS: si curl ve la respuesta y el navegador no, es este síntoma, no un 500.

Arreglo: o el proxy de Vite de 06-react.md, que hace que el navegador llame a su mismo origen, o cors({ origin: "http://localhost:5173" }) en la API. Tiene que aparecer también en la respuesta al preflight OPTIONS. Si solo lo pones en GET, el POST con Content-Type: application/json sigue fallando porque el navegador pregunta antes con OPTIONS. El paquete cors contesta ese OPTIONS. No uses origin: "*" si la petición lleva cookies o cabecera Authorization que quieras limitar.

404 en una ruta que sí existe

Causa habitual:

  1. El método no coincide: el cliente hace GET y la ruta es POST.
  2. Falta o sobra una barra, o el prefijo /api.
  3. Una ruta /:id se declaró antes y se comió el nombre fijo.
  4. Hay dos procesos y estás pegándole al viejo, que no tiene la ruta. El del puerto nuevo sí.

Arreglo: copia del código la ruta y el método y pégalos en curl -i -X POST http://localhost:3000/api/notas. Si curl da 404, el proceso que escucha no es el código que estás leyendo (reinicia, mira el log de arranque, confirma el puerto). Si curl da 201 y el navegador da 404, compara la URL de la pestaña Red carácter por carácter.

400 con un cuerpo que tú crees válido

Causa habitual: el JSON manda titulo y el servidor lee text. O el string trae espacios y al recortar queda vacío. O express.json() no corrió y estás validando undefined.

Arreglo: en el manejador, durante el diagnóstico, console.log(req.body) y mira la terminal de Node, no la del navegador. Ajusta el nombre del campo a uno solo (en esta biblioteca, text y email). Responde el 400 con el motivo concreto ("text debe tener entre 1 y 2000 caracteres"), no con "datos inválidos" para todos los casos, o no podrás distinguirlos desde la pantalla.

500 y la pantalla no dice la causa

Causa habitual: una excepción en la ruta. El JSON solo dice "Error interno" a propósito. La causa está en la terminal donde corre Node, en la línea que imprimió console.error(error).

Arreglo: lee esa línea. Las más comunes aquí son relation "notes" does not exist (08-postgresql.md) y ECONNREFUSED a Postgres o a Redis. No envíes error.message al cliente para "verlo en la pantalla": vuelve a filtrar datos de la base. Si estás solo en local, míralo en el log.

El cuerpo de la petición llega vacío

Causa habitual: falta la cabecera Content-Type: application/json, y Express no parsea el cuerpo. O el cliente mandó un objeto de JavaScript sin JSON.stringify. O un GET con cuerpo: muchos servidores lo ignoran; los filtros van en la query (?cursor=).

Arreglo: en la pestaña Red, la petición debe mostrar el cuerpo como JSON y la cabecera correcta. El fetch de 03-javascript.md ya la pone. Con curl, sin -H "Content-Type: application/json", req.body sale {} y la validación responde 400. Ese 400 es la pista, no un fallo de PostgreSQL.

Cómo comprobar

  1. Los cinco métodos de la tabla, con curl, devuelven el código de la tabla.
  2. Un POST sin text devuelve 400 y no crea fila. Compruébalo con un SELECT count(*).
  3. Un GET de un id que no existe devuelve 404, no 500 ni null.
  4. Con Postgres parado, el GET devuelve 500 y el log tiene ECONNREFUSED, y el JSON no incluye la cadena de conexión.
  5. Desde el origen del frontend, el POST no muestra el error de CORS. Desde curl, el mismo POST sigue funcionando.

JWT y sesión

JWT (JSON Web Token) es una cadena firmada que el servidor puede verificar sin guardarla. Sirve para saber quién llama. No sirve para esconder datos: la parte del medio se lee en claro. No pongas ahí la contraseña, el hash ni datos que el usuario no debería ver en su propio navegador.

La contraseña se comprueba una vez, en el login, contra un hash guardado en PostgreSQL. Después el cliente presenta el token. El mapa llama a esta caja "JWT Auth". La ficha de al lado, Redis, no hace falta para el básico ni para el intermedio.

Cuándo usarlo y cuándo no

Úsalo cuando haya usuarios y filas que son suyas. Hasta entonces, la API abierta del CRUD es suficiente para practicar SQL.

No uses un JWT como permiso permanente de años, ni lo guardes en localStorage si puedes evitarlo: cualquier script metido en la página lo lee. El patrón intermedio deja el recuerdo de la sesión en una cookie httpOnly, que el JavaScript de la página no puede leer.

import bcrypt from "bcryptjs";
import jwt from "jsonwebtoken";

const DUMMY_HASH = bcrypt.hashSync("no-es-una-cuenta", 12);

app.post("/api/usuarios", asyncRoute(async (req, res) => {
  const email = typeof req.body?.email === "string" ? req.body.email.trim().toLowerCase() : "";
  const password = typeof req.body?.password === "string" ? req.body.password : "";
  if (!email.includes("@") || password.length < 10) {
    res.status(400).json({ error: "Correo o contraseña no válidos" });
    return;
  }
  const passwordHash = await bcrypt.hash(password, 12);
  try {
    const { rows } = await pool.query(
      "INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email",
      [email, passwordHash],
    );
    res.status(201).json(rows[0]);
  } catch (error) {
    if (error.code === "23505") {
      res.status(409).json({ error: "Ese correo ya está registrado" });
      return;
    }
    throw error;
  }
}));

app.post("/api/sesion", asyncRoute(async (req, res) => {
  const email = typeof req.body?.email === "string" ? req.body.email.trim().toLowerCase() : "";
  const password = typeof req.body?.password === "string" ? req.body.password : "";
  const { rows } = await pool.query(
    "SELECT id, password_hash FROM users WHERE email = $1",
    [email],
  );
  const user = rows[0];
  const coincide = await bcrypt.compare(password, user?.password_hash ?? DUMMY_HASH);
  if (!user || !coincide) {
    res.status(401).json({ error: "Credenciales incorrectas" });
    return;
  }
  const token = jwt.sign({ sub: String(user.id) }, process.env.JWT_SECRET, { expiresIn: "1h" });
  res.json({ token });
}));

DUMMY_HASH es un hash bcrypt de verdad, generado al arrancar, de una contraseña que no corresponde a ninguna cuenta. Cuando el correo no existe, compare trabaja el mismo tipo de cálculo que cuando existe. Así un atacante no distingue "no hay usuario" de "mala contraseña" midiendo el reloj. La respuesta es la misma frase en los dos casos. Si la contraseña escrita coincidiera con la de relleno y el usuario no existe, la condición !user igual responde 401.

Proteger una ruta:

function exigirUsuario(req, res, next) {
  const cabecera = req.get("authorization") ?? "";
  const token = cabecera.startsWith("Bearer ") ? cabecera.slice(7) : "";
  if (!token) {
    res.status(401).json({ error: "Falta sesión" });
    return;
  }
  try {
    const datos = jwt.verify(token, process.env.JWT_SECRET);
    req.userId = Number(datos.sub);
    next();
  } catch {
    res.status(401).json({ error: "Sesión no válida" });
  }
}

app.get("/api/notas", exigirUsuario, asyncRoute(async (req, res) => {
  const { rows } = await pool.query(
    "SELECT id, text, created_at FROM notes WHERE user_id = $1 ORDER BY id LIMIT 20",
    [req.userId],
  );
  res.json(rows);
}));

Intermedio

El básico obliga al frontend a guardar el token. Si lo dejas en una variable, recargar da 401. Si lo dejas en localStorage, recargar funciona y cualquier XSS se lleva la sesión. El término medio de esta biblioteca: el access token dura poco y el recuerdo es una cookie que el JavaScript no lee.

  • Access token: JWT de 15 minutos, en memoria, cabecera Authorization. Se pierde al recargar, a propósito.
  • Refresh: valor opaco (no hace falta que sea un JWT), en cookie httpOnly, SameSite=Lax, Secure en producción, Path=/api/sesion, caducidad de 14 días.
  • El servidor guarda solo el hash de ese valor (en la tabla sessions). Si te copian la base, no pueden presentar la cookie.

}

  const refresh = randomBytes(32).toString("base64url");
  await pool.query(
    `INSERT INTO sessions (user_id, token_hash, expires_at)
     VALUES ($1, $2, now() + interval '14 days')`,
    [user.id, hashToken(refresh)],
  );
  res.cookie("refresh", refresh, {
    httpOnly: true,
    sameSite: "lax",
    secure: process.env.NODE_ENV === "production",
    path: "/api/sesion",
    maxAge: 14 * 24 * 60 * 60 * 1000,
  });
  res.json({ token: access });
}));

app.post("/api/sesion/renovar", asyncRoute(async (req, res) => {
  const refresh = req.cookies?.refresh ?? "";
  const { rows } = await pool.query(
    `SELECT user_id FROM sessions
     WHERE token_hash = $1 AND expires_at > now()`,
    [hashToken(refresh)],
  );
  if (!rows[0]) {
    res.status(401).json({ error: "Sesión no válida" });
    return;
  }
  const access = jwt.sign({ sub: String(rows[0].user_id) }, process.env.JWT_SECRET, { expiresIn: "15m" });
  res.json({ token: access });
}));

app.delete("/api/sesion", asyncRoute(async (req, res) => {
  const refresh = req.cookies?.refresh ?? "";
  await pool.query("DELETE FROM sessions WHERE token_hash = $1", [hashToken(refresh)]);
  res.clearCookie("refresh", { path: "/api/sesion" });
  res.status(204).end();
}));

Hace falta cookie-parser (npm install cookie-parser y app.use(cookieParser()) antes de las rutas). La tabla:

CREATE TABLE sessions (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users (id),
  token_hash text NOT NULL UNIQUE,
  expires_at timestamptz NOT NULL
);

El frontend, al cargar la app, llama a POST /api/sesion/renovar con credentials: "include". Si responde 200, guarda el access token en memoria y sigue. Si responde 401, muestra el login. Eso es lo que quita el 401 al recargar sin meter el token en localStorage.

const respuesta = await fetch("/api/sesion/renovar", {
  method: "POST",
  credentials: "include",
});

credentials: "include" es lo que manda la cookie. Sin eso, el navegador la guarda y no la envía, y parece que "la cookie no existe". El caso está cruzado con 12-app-completa.md.

Cerrar sesión borra la fila y la cookie. Cerrar solo la pestaña no cierra sesión: el refresh sigue válido hasta el DELETE o hasta los 14 días. En una app pequeña eso es aceptable si el botón "Salir" sí llama al DELETE.

Avanzado

Lo que se rompe cuando roban una cookie o cuando cambias el secreto un martes.

Rotación. En cada renovar, borra el refresh usado y emite otro. Si el mismo refresh llega dos veces, asume que se copió: borra todas las sesiones de ese usuario y responde 401. El cliente legítimo tendrá que entrar otra vez; el copiado también. Es mejor que dejar las dos sesiones vivas.

const usado = await pool.query(
  "DELETE FROM sessions WHERE token_hash = $1 AND expires_at > now() RETURNING user_id",
  [hashToken(refresh)],
);
if (!usado.rows[0]) {
  res.status(401).json({ error: "Sesión no válida" });
  return;
}

El INSERT del refresh nuevo va en la misma transacción que ese DELETE.

Revocar al cambiar la contraseña: DELETE FROM sessions WHERE user_id = $1. Si no, el refresh robado sigue renovando access tokens aunque el usuario haya puesto una clave nueva.

JWT_SECRET distinto en cada entorno (tu máquina, el servidor). Rotarlo invalida todos los access tokens, que duran 15 minutos: es soportable. No reutilices un secreto de ejemplo. Si el secreto se filtró, el arreglo es rotarlo y borrar sessions, no "esperar a que caduquen" los refresh de 14 días.

secure: true solo cuando la página es HTTPS. En local, con HTTP, una cookie Secure no se guarda y el síntoma parece un login roto. Por eso va atada a NODE_ENV === "production". En el servidor, HTTPS es obligatorio antes de poner producción. Ver 15-despliegue.md.

CSRF. Una cookie se envía sola en una navegación. Con SameSite=Lax, un formulario de otro sitio no la manda en un POST cruzado. No bajes a SameSite=None para "arreglar" el frontend en otro dominio: si la API y la página están en orígenes distintos y necesitas la cookie, estás en el caso avanzado de CORS con credentials y una lista de orígenes concreta, más un token CSRF de doble envío. Mientras puedas, sirve la página y la API en el mismo dominio (Nginx) y quédate en Lax.

No metas permisos finos solo dentro del JWT ({ admin: true }) sin poder invalidarlos. Un JWT de 15 minutos con un rol viejo es un cuarto de hora de más. Para una app de notas, el permiso es "esta fila tiene tu user_id". No hace falta un sistema de roles. Cuando lo necesites, la fuente del rol es la base, leída al renovar, no un booleano eterno dentro del token.

Errores frecuentes

401 al recargar, justo después de haber entrado

Causa habitual: el access token está en una variable de React y la recarga la vacía. El básico hace eso a propósito.

Arreglo: pasa al patrón intermedio (POST /api/sesion/renovar al arrancar la app) o, si todavía estás en el básico y solo quieres terminar el día, guarda el token en sessionStorage sabiendo que un XSS se lo lleva. No lo dejes en localStorage "porque es más fácil" y lo olvides ahí. sessionStorage al menos muere al cerrar la pestaña.

Si ya usas la cookie y sigues viendo 401 al recargar, el renovar no se está llamando, o la cookie no se envía: sigue en el síntoma de la cookie de 12-app-completa.md.

401 con jwt expired

Causa habitual: el access token llegó a su expiresIn. Con 15 minutos pasa en medio del trabajo. El mensaje exacto lo produce jsonwebtoken cuando verificas; si tu catch lo convierte todo en "Sesión no válida", lo verás en el log solo si lo imprimes.

Arreglo: en el cliente, un 401 en una ruta normal dispara un solo POST /api/sesion/renovar y, si sale bien, repite la petición original con el access nuevo. Si el renovar también da 401, al login. No alargues el access a 30 días para no implementar el renovar: ese token robado sirve un mes.

Comprueba el reloj del servidor. Un VPS con la hora mal marca tokens como caducados al nacer. date -u en el servidor tiene que parecerse a la hora real.

403 con un token que sí es válido

Causa habitual: el token identifica a Ada y la nota es de otra persona. Eso no es un 401. El 401 dice "no sé quién eres". El 403 dice "sé quién eres y esta fila no es tuya". También aparece si exiges un rol que el usuario no tiene.

Arreglo: la consulta lleva WHERE id = $1 AND user_id = $2. Si no devuelve fila, responde 404, no 403, cuando no quieras revelar que el id existe. Reserva el 403 para una acción que el usuario entiende que no puede hacer (borrar la cuenta de otro, por ejemplo). No cambies el 403 por un 200 vacío.

El login dice siempre "credenciales incorrectas"

Causa habitual, con la contraseña bien escrita:

  1. El correo se guardó con mayúsculas y lo buscas en minúsculas, o al revés. El alta de esta ficha guarda toLowerCase(). Un alta anterior, no.
  2. bcrypt.compare contra un hash que no es bcrypt (pegaste la contraseña en claro en password_hash al probar en psql).
  3. JWT_SECRET vacío. Eso falla al firmar, y si el error cae en un catch demasiado amplio, lo conviertes en 401.
  4. El body no llega: 09-api-rest.md.

Arreglo: en psql, SELECT email, left(password_hash, 4) FROM users WHERE email = 'ada@example.com';. El hash de bcrypt empieza por $2. Si la fila no está, el correo no es el que crees. Si el hash no empieza por $2, vuelve a registrar. Mira el log antes de asumir que la contraseña no coincide: un 500 tragado no es una credencial mala.

Cómo comprobar

  1. Alta, login, GET /api/notas con el token, y el mismo GET sin token (401).
  2. Un segundo usuario no ve las notas del primero.
  3. Con el patrón intermedio: recargar la página vuelve a entrar sin pedir la contraseña, y "Salir" hace que el renovar responda 401.
  4. Un token recortado o con un carácter cambiado responde 401.
  5. El .env no está en Git y el secreto no aparece en el JSON de ninguna respuesta.

Si esto no alcanza

jsonwebtoken verify, bcrypt compare, MDN set-cookie HttpOnly, MDN fetch credentials.

El mensaje jwt expired y invalid signature se buscan literales.

Checkpoint — login (60 a 90 minutos)

Sobre la API de notas:

  • Registro con contraseña de al menos 10 caracteres, guardada como hash. En psql no se lee la contraseña.
  • Login que devuelve un token, y GET /api/notas filtrado por el usuario del token.
  • Dos usuarios de prueba, cada uno con una nota, sin poder leerse entre sí.
  • Recargar no deja la app en un 401 mudo: o renuevas con la cookie, o la pantalla pide entrar otra vez y lo explica.

Redis

Redis guarda valores en memoria y los devuelve en poco tiempo, con una caducidad. En esta biblioteca hace tres trabajos concretos: cachear un listado, limitar ráfagas de peticiones y, si quieres, guardar el refresh de la sesión fuera de PostgreSQL. No sustituye a PostgreSQL. Si Redis se vacía, la app tiene que seguir: irá más lenta o pedirá entrar de nuevo, pero no habrá perdido las notas.

Cuándo usarlo y cuándo no

Úsalo cuando la misma lectura cara se repite, o cuando un contador tiene que vivir unos minutos y no te importa perderlo al reiniciar.

No lo uses como única copia de las notas, de los usuarios o de los pagos. Tampoco hace falta el día del CRUD simple: mételo cuando el listado ya sale de Postgres y quieres dejar de pegarle en cada refresco.

Se puede hacer una caché parecida en la propia base o en memoria del proceso. La memoria del proceso no se comparte si mañana arrancas dos Node. Redis sí.

Básico

Redis escucha en el puerto 6379. En el servidor Linux:

sudo apt update
sudo apt install redis-server
redis-cli PING

Tiene que responder PONG. En Windows nativo no hay un Redis oficial equivalente. Practica dentro de WSL con los mismos comandos, o con una línea de Docker si ya lo usas: docker run --name redis-local -p 6379:6379 redis:7. Es una herramienta de práctica, no otra caja del mapa.

.env

REDIS_URL=redis://127.0.0.1:6379
npm install redis

src/redis.js:

import { createClient } from "redis";

export const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (error) => console.error("redis", error.message));
await redis.connect();

En server.js el await de arriba solo funciona si el archivo es el de entrada. Si redis.js se importa desde varios sitios, conecta una vez desde server.js y exporta el cliente ya creado, sin await en la cima de un módulo que se importe dos veces. Forma simple y suficiente:

import { createClient } from "redis";

export const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (error) => console.error("redis", error.message));

export function conectarRedis() {
  if (!redis.isOpen) return redis.connect();
}

Comandos que cubren el checkpoint, en redis-cli:

SET nota:1 "Revisar el formulario" EX 60
GET nota:1
TTL nota:1
DEL nota:1

EX 60 borra la clave al minuto. TTL dice cuántos segundos quedan. -2 significa que ya no está.

Desde Node:

await redis.set("nota:1", "Revisar el formulario", { EX: 60 });
const valor = await redis.get("nota:1");

Los valores son texto. Un objeto se guarda con JSON.stringify y se lee con JSON.parse.

Intermedio

Caché del listado de notas de un usuario. La clave incluye el usuario. Una clave notas global mezcla los listados de todo el mundo: es una fuga, no una optimización.

const clave = `notas:${userId}`;
const cacheado = await redis.get(clave);
if (cacheado) {
  res.json(JSON.parse(cacheado));
  return;
}
const { rows } = await pool.query(
  "SELECT id, text, created_at FROM notes WHERE user_id = $1 ORDER BY id LIMIT 20",
  [userId],
);
await redis.set(clave, JSON.stringify(rows), { EX: 30 });
res.json(rows);

Al crear, editar o borrar una nota de ese usuario, la caché miente hasta que caduque. Bórrala en la misma petición que escribe:

await pool.query("INSERT INTO notes (user_id, text) VALUES ($1, $2)", [userId, text]);
await redis.del(`notas:${userId}`);

Treinta segundos es un número de práctica. Súbelo solo si el listado es caro y puedes tolerar ese retraso. En una app de notas personales, invalidar al escribir importa más que alargar el EX.

Límite de intentos de login, para que un bucle no pruebe contraseñas sin freno:

const clave = `login:${email}`;
const intentos = await redis.incr(clave);
if (intentos === 1) await redis.expire(clave, 15 * 60);
if (intentos > 10) {
  res.status(429).json({ error: "Demasiados intentos. Espera un cuarto de hora." });
  return;
}

429 es el código de "demasiado". INCR y EXPIRE tienen una carrera diminuta si el proceso muere entre los dos; para un login es aceptable. Si el primer intento no pone caducidad, la clave vive para siempre y el usuario queda bloqueado. Por eso el expire va cuando el contador pasa a ser 1.

Redis caído no tiene que tumbar el listado. Tiene que tumbar el límite de login solo si prefieres negar el login a dejarlo sin límite. Decisión de esta biblioteca: si Redis no responde, el listado se sirve desde Postgres y el login se niega con 503. Un login sin límite, en silencio, es peor que una pausa.

let cacheado = null;
try {
  cacheado = await redis.get(clave);
} catch (error) {
  console.error("redis", error.message);
}
if (!cacheado) {
  // consulta a Postgres, y el set va en su propio try
}

Avanzado

Lo que se rompe cuando hay más de un proceso o cuando la memoria se llena.

Dos Node detrás de Nginx comparten Redis y no comparten la memoria del proceso. El contador de login y la caché tienen que estar en Redis para que el límite sea de verdad. Si el contador vive en una variable, cada proceso tiene el suyo y el atacante tiene un cupo por proceso.

Carrera de la caché. Dos peticiones ven la clave vacía, las dos consultan Postgres, las dos escriben. El resultado es correcto, solo redundante. No hace falta un candado para un listado de notas. Sí hace falta no cachear respuestas de error: un 500 guardado con EX 30 convierte un fallo corto en un fallo de medio minuto.

maxmemory. Si no pones tope, Redis crece hasta que el sistema mata el proceso o el disco de swap se come la máquina (Redis en swap va muy mal). En el servidor, en redis.conf:

maxmemory 256mb
maxmemory-policy allkeys-lru

allkeys-lru tira las claves menos usadas cuando llega al tope, incluidas las de sesión si las guardaste aquí. Por eso las notas no viven solo en Redis. Si guardas el refresh de 10-jwt.md en Redis en vez de en sessions, un desalojo cierra sesiones al azar: es el síntoma de abajo. Para una app pequeña deja los refresh en PostgreSQL y usa Redis para caché y contadores, que sí se pueden perder.

No expongas el puerto 6379 a internet. bind 127.0.0.1 y, si hay contraseña, requirepass en el mismo archivo, y REDIS_URL=redis://:clave@127.0.0.1:6379. La clave va en .env, no en el repositorio. Un Redis sin contraseña y con el puerto abierto en el grupo de seguridad se usa para minar o para colarse en la red; no es un riesgo teórico. Al desplegar, el grupo de seguridad no incluye el 6379. Ver 20-seguridad-minima.md.

Caché y usuario. La clave notas:${userId} ya aísla. No cachees GET /api/notas/15 en una clave nota:15 compartida si la respuesta depende de quién pregunta: o la clave incluye el usuario, o no se cachea.

Errores frecuentes

Redis connection refused

Causa habitual: el servicio no está arrancado, REDIS_URL apunta a otro host, o en Windows estás llamando a 127.0.0.1 y Redis está dentro de WSL con otra IP.

Arreglo: redis-cli -u "$REDIS_URL" PING con la misma URL que Node. En Linux, sudo systemctl status redis-server (el nombre a veces es redis). Arranca con sudo systemctl start redis-server. Si PING responde y Node no conecta, el proceso de Node no vio REDIS_URL: 07-nodejs.md.

La API devuelve datos viejos

Causa habitual: escribiste en Postgres y no hiciste DEL de notas:${userId}, o borraste otra clave (notas sin el id). También pasa si el SET se hace antes del COMMIT y la otra petición lee la caché nueva mientras la transacción aún no se ve, o al revés: cacheas y luego el INSERT falla.

Arreglo: escribe en Postgres, confirma que no hubo error, y solo entonces DEL. No hagas SET del listado nuevo a mano si es fácil equivocarse en la forma: borrar la clave obliga al próximo GET a leer la base. Comprueba con redis-cli GET notas:1 justo después del POST. Tiene que decir (nil) o el JSON que ya incluye la nota nueva.

La sesión desaparece sola

Causa habitual: el refresh está en Redis con un EX corto, o allkeys-lru lo desalojó, o guardaste la sesión en la memoria del proceso y nodemon reinició al guardar un archivo. Un reinicio de Node no borra Redis ni Postgres; sí borra las variables.

Arreglo: redis-cli TTL sesion:EL_ID. Si devuelve un número pequeño, la caducidad es esa. Si la sesión debe durar 14 días, el EX está mal puesto (segundos, no días: 14 días son 1209600). Si las sesiones no deben perderse al llenarse la memoria, muévelas a la tabla sessions de 10-jwt.md y deja Redis para la caché. Mira también la cookie: una cookie de sesión del navegador, sin maxAge, muere al cerrar el navegador aunque Redis siga teniendo la clave.

Cómo comprobar

  1. redis-cli PING responde PONG en el mismo sitio donde corre Node.
  2. El primer GET /api/notas y el segundo devuelven lo mismo, y en el log se ve una sola consulta SQL (pon un console.log delante del pool.query mientras lo compruebas, y quítalo).
  3. Después de un POST, el siguiente GET ya incluye la nota, sin esperar 30 segundos.
  4. El intento 11 de login en un cuarto de hora devuelve 429.
  5. Con Redis parado, el GET /api/notas sigue respondiendo desde Postgres.

Si esto no alcanza

Documentación de Redis: redis set ex, redis incr, redis maxmemory-policy, redis ttl.

Del paquete de Node: node-redis set options EX.

Checkpoint — caché (45 minutos)

Con la API de notas ya filtrada por usuario:

  • Redis local que responde PONG.
  • El listado se cachea 30 segundos por usuario.
  • Un alta borra la caché de ese usuario y no la de otro. Lo compruebas con dos usuarios.
  • Redis parado no impide leer las notas.

useEffect(() => {
  const controlador = new AbortController();
  fetch("/api/sesion/renovar", {
    method: "POST",
    credentials: "include",
    signal: controlador.signal,
  })
    .then((respuesta) => {
      if (!respuesta.ok) throw new Error("sin sesion");
      return respuesta.json();
    })
    .then((datos) => setToken(datos.token))
    .catch((error) => {
      if (error.name !== "AbortError") setToken(null);
    });
  return () => controlador.abort();
}, []);

setToken(null) muestra el formulario de login. Un token string muestra la lista. Las llamadas a /api/notas mandan el token:

await fetch("/api/notas", {

});

Intermedio

El recorrido de una persona, de punta a punta, con los estados que no son el caso feliz.

  1. Registro. Si el correo existe, la API responde 409 y la pantalla dice que ya está registrado, no "error interno".
  2. Login. Un 401 muestra "credenciales incorrectas". Un 429 muestra la espera. Ver 11-redis.md.
  3. Lista. Estados cargando, error y vacío, como en el checkpoint de React. Vacío no es un error: es una lista de cero filas después de un 200.
  4. Alta. El botón se desactiva mientras dura el POST. Al volver el 201, se vuelve a pedir el listado (o se inserta la nota devuelta) y la caché ya fue borrada en el servidor.
  5. Borrado de una nota que ya no está (la borraste en otra pestaña): la API responde 404 y la pantalla quita la fila igual, o muestra "ya no estaba". No dejes un 404 sin manejar: parece que el botón no funciona.
  6. Salir. DELETE /api/sesion con credentials: "include", token de memoria a null, lista desaparecida de la pantalla. Las filas siguen en Postgres. Lo compruebas en psql.

Variables separadas por carpeta. El frontend solo recibe lo que empiece por VITE_. En este montaje, con el proxy, no necesita la URL de la API. No crees VITE_DATABASE_URL: quedaría dentro del JavaScript público.

Un solo repositorio o dos, como prefieras. Si son dos, los dos tienen su .gitignore y ninguno tiene el .env. La colección de curl (o un archivo api.md con los comandos que ya te funcionaron) vive en el repo de la API para poder probar sin abrir React.

Cuando un fallo cruce capas, aplica 00-metodo-sin-ia.md antes de cambiar las dos a la vez. La pregunta de corte es: ¿curl, con el mismo token, hace lo correcto?

  • Si curl falla, no toques React.
  • Si curl va bien y el navegador no, mira la pestaña Red: URL, código, cabecera Authorization, cabecera Cookie.

Lo que se rompe al salir de tu portátil. El despliegue paso a paso está en 15-despliegue.md. Aquí, las decisiones que tienen que estar tomadas antes de copiar archivos a un servidor.

Un origen. La página y la API se sirven en https://notas.example.com y https://notas.example.com/api. La cookie Secure se guarda, SameSite=Lax basta y no configuras CORS. Partir la API a api.notas.example.com te obliga al caso CORS con credenciales. No lo hagas en la primera publicación.

Secretos distintos a los de tu .env local. El de local tiene la contraseña notas y un JWT de prueba. El servidor tiene otros, en el entorno de systemd, no en un .env copiado por SCP "para ir rápido". Si copias el de local, rota las claves en cuanto te des cuenta y trata el de local como filtrado si el servidor es de alguien más.

Migraciones antes de arrancar el proceso nuevo. Orden en un despliegue:

  1. Copia de seguridad (pg_dump) si ya hay datos que importan.
  2. node src/migrate.js con el código nuevo y la base vieja todavía sirviendo, solo si esa migración es compatible con el código viejo (añadir una columna con default lo es; borrar una columna que el código viejo usa, no).
  3. Arrancar el Node nuevo.
  4. curl al /api/salud y un login de prueba.
  5. Si el paso 4 falla, el proceso anterior vuelve. Por eso la migración no puede ser un callejón sin vuelta el mismo día que aprendes a desplegar. Practica el "volver" en local: migra, arranca, para, arranca el código anterior.

Salud de verdad. /api/salud que solo responde { ok: true } no mira la base. Uno útil, para ti y para Monit:

app.get("/api/salud", asyncRoute(async (_req, res) => {
  await pool.query("SELECT 1");
  const pong = await redis.ping();
  if (pong !== "PONG") throw new Error("redis");
  res.json({ ok: true });
}));

Si la base está caída, esto da 500. Monit o el balanceador pueden usarlo. No lo protejas con JWT: el vigilante no tiene usuario. No imprimas versiones ni la cadena de conexión en el JSON.

Límites que ya quedaron decididos en las otras fichas y aquí solo se confirman: cuerpo de 32 KB, texto de nota hasta 2000, login a 10 intentos por cuarto de hora, pool de Postgres uno solo, Redis solo en 127.0.0.1.

Errores frecuentes

La cookie no se guarda

Causa habitual:

  1. El frontend llama a http://localhost:3000 desde http://localhost:5173 y la cookie queda asociada al 3000, mientras el renovar del navegador va al 5173. El proxy de Vite evita el corte.
  2. Falta credentials: "include" en el fetch del login y en el del renovar.
  3. secure: true con la página en http://. El navegador tira la cookie.
  4. path: "/api/sesion" y estás mirando la cookie en una petición a /api/notas. No va en esa petición, y está bien: el refresh solo debe viajar al renovar y al cerrar. El listado usa el access token, no la cookie.
  5. SameSite y un origen cruzado. Vuelve al punto 1.

Arreglo: en la pestaña Red, abre la respuesta del POST /api/sesion. Tiene que haber Set-Cookie con HttpOnly y Path=/api/sesion. Luego abre POST /api/sesion/renovar y confirma que la petición lleva Cookie. Si Set-Cookie está y la petición siguiente no la manda, el origen o el credentials no cuadran. Si Set-Cookie ni siquiera está, el servidor no entró en el res.cookie (el login falló antes, o cookie-parser no cambia este síntoma: quien escribe la cookie es res.cookie).

En local va y en el servidor no

Causa habitual: no es "la nube". Es una de estas diferencias, y curl en el servidor las separa:

  1. .env distinto o ausente. PORT, DATABASE_URL, JWT_SECRET, NODE_ENV.
  2. Migraciones sin aplicar en esa base. relation "notes" does not exist.
  3. El frontend publicado es una build vieja (dist/ generado cuando la API aún no pedía Authorization).
  4. HTTPS y cookie Secure, o al revés: NODE_ENV no es production y mezclas criterios.
  5. El proceso escucha en 127.0.0.1 y Nginx no puede llegar, o escucha en un puerto y Nginx apunta a otro. Eso ya es 15-despliegue.md.

Arreglo: entra por SSH y ejecuta el mismo curl contra http://127.0.0.1:3000/api/salud y contra el login. Si ahí funciona y por el dominio no, el fallo es Nginx, DNS o el certificado. Si ahí ya falla, no mires el dominio: es el mismo fallo que en local, con otro entorno. Compara systemctl cat notas con tu .env local, nombre por nombre, sin copiar los secretos al chat ni a un archivo del repo.

Cómo comprobar

Recorrido, en este orden, sin saltar:

  1. psql: cero notas para un usuario nuevo.
  2. Registro desde la pantalla.
  3. Login, alta de una nota, recarga de la página: la nota sigue y no pide la contraseña otra vez (renovar).
  4. Segundo usuario en una ventana privada: no ve esa nota.
  5. Salir en la primera ventana: la recarga pide contraseña.
  6. redis-cli GET de la clave de ese usuario después del alta: vacía o actualizada, no el listado anterior.
  7. npm run build del frontend termina. El dev de Vite no es la app que vas a copiar al servidor.

Si esto no alcanza

No busques "app completa node react". Busca el síntoma concreto en 00-indice-de-sintomas.md. Si el fallo es de encaje (cookie, origen, entorno), quédate en esta ficha. Si es de una sola capa, salta a su archivo.

Checkpoint — app completa (medio día, partido en dos sentadas si hace falta)

Una app que otra persona puede usar en tu máquina, con instrucciones de tres líneas para arrancar Postgres, Redis, la API y el frontend:

  • Cuenta, login, listado, alta, edición, borrado.
  • Los datos siguen tras reiniciar Node.
  • Dos cuentas no se ven entre sí.
  • La lista no muestra datos de antes de un borrado.
  • Hay un curl escrito en un archivo del repo que crea una nota sin abrir el navegador.

Hecho cuando esa otra persona (o tú, al día siguiente, en una terminal nueva) lo arranca solo con esas instrucciones y el .env de ejemplo sin secretos reales (.env.example, con los nombres y sin los valores).

Publicarla es el checkpoint de 15-despliegue.md, no este.

Linux

En el servidor, la app no tiene escritorio. Entras por una terminal, miras logs, mueves archivos y dejas el proceso a cargo de systemd. El mapa llama a esta caja "Linux Basics". Los ejemplos son de Ubuntu, que es lo habitual en una EC2 nueva. En tu PC con Windows practicas lo mismo dentro de WSL, o directo en el servidor el día del despliegue.

PowerShell no entiende estos comandos. La terminal del servidor es bash.

Cuándo usarlo y cuándo no

Úsalo en cuanto la app salga de tu portátil. También para confirmar, por SSH, que un fallo "de AWS" en realidad es un proceso parado.

No hace falta memorizar la administración entera. Con el bloque de abajo se opera la app de esta biblioteca. Lo demás se busca con el nombre del comando.

Básico

Entrar y mirar sin cambiar nada:

ssh -i ~/.ssh/notas.pem ubuntu@LA_IP
pwd
whoami
ls -la
df -h
free -h

df -h es el disco. free -h es la memoria. ls -la muestra dueños y permisos. pwd es la carpeta actual: muchos "no encuentro el .env" son un cd que no se hizo.

Archivos y procesos:

cd /opt/notas
cp .env.example .env
nano .env
mkdir -p /var/log/notas
ps aux | grep node
ss -ltnp | grep 3000

nano guarda con Ctrl+O y sale con Ctrl+X. Si no está, sudo apt install nano. ss muestra quién escucha. Es el mismo dato que el síntoma del puerto en 07-nodejs.md.

Instalar lo que la app necesita, una vez:

sudo apt update
sudo apt install nginx postgresql redis-server

Node no siempre va en los repos de Ubuntu a una versión LTS reciente. Si node -v es viejo o no existe, usa el paquete de NodeSource o el tarball oficial de nodejs.org para la LTS, y vuelve a abrir la sesión SSH antes de concluir que node "no se instaló".

Permisos, en una frase: r leer, w escribir, x entrar en una carpeta o ejecutar. chmod 600 .env deja el secreto legible solo por su dueño. chown ubuntu:ubuntu /opt/notas entrega la carpeta al usuario que corre la app. Ese usuario no es root.

sudo mkdir -p /opt/notas
sudo chown ubuntu:ubuntu /opt/notas
chmod 600 /opt/notas/.env

Un comando con sudo corre como root. Úsalo para instalar y para tocar /etc. No para npm install ni para node src/server.js: si no, los archivos quedan de root y al día siguiente el usuario de la app no puede escribir.

Intermedio

systemd mantiene el proceso vivo y lo levanta al reiniciar la máquina. /etc/systemd/system/notas.service:

[Unit]
Description=API de notas
After=network.target postgresql.service redis-server.service

[Service]
User=ubuntu
WorkingDirectory=/opt/notas
EnvironmentFile=/opt/notas/.env
ExecStart=/usr/bin/node src/server.js
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target

EnvironmentFile exige CLAVE=valor, sin export, sin comillas raras. Es el reemplazo de --env-file en el servidor. El proceso no debe depender de que tú hayas hecho cd a mano.

sudo systemctl daemon-reload
sudo systemctl enable --now notas
systemctl status notas --no-pager
journalctl -u notas -n 50 --no-pager

enable lo arranca en cada boot. restart, stop y start son los otros tres que vas a usar. Después de cambiar el .service o el .env, daemon-reload y systemctl restart notas. Un restart sin daemon-reload no ve el unit nuevo.

Nginx como puerta de entrada queda en 15-despliegue.md. Aquí solo el hábito de leer el log:

journalctl -u notas -f
journalctl -u nginx -n 50 --no-pager

-f sigue el log en vivo. Ctrl+C sale de ese seguimiento y no para la app.

Firewall del propio Linux, si está activo:

sudo ufw status
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

No abras 5432 ni 6379 en ufw. Postgres y Redis se quedan en localhost. El grupo de seguridad de AWS es otra cerradura distinta: las dos tienen que permitir el puerto, o la conexión no entra. Ver 14-aws-basico.md.

Avanzado

Lo que se rompe a las pocas semanas, no el primer día.

Disco lleno por logs. journalctl tiene su propio tope. Configúralo antes de necesitarlo, en /etc/systemd/journald.conf:

SystemMaxUse=200M
sudo systemctl restart systemd-journald

Eso no borra los logs de Nginx. Esos van en /var/log/nginx/ y logrotate ya viene en Ubuntu para rotarlos. Si añadiste un log propio en /var/log/notas/app.log, logrotate no lo conoce hasta que escribas una regla. Más simple: no abras un archivo de log y deja que el proceso escriba a stdout. systemd ya lo guarda. Es el mismo criterio de 07-nodejs.md.

Actualizaciones de seguridad, no "upgrade" el día de una entrega:

sudo apt update
sudo apt upgrade

Hazlo con la app arrancada y cinco minutos para reiniciar si el paquete lo pide ([restart required]). Un dist-upgrade o un cambio de versión mayor de PostgreSQL no es este comando. Léelo antes de aceptarlo.

Usuario de la app separado del usuario con el que haces SSH, cuando ya no estés practicando:

User=notas

El usuario notas no tiene shell de login (adduser --system --group notas crea uno de sistema). Tú entras como ubuntu, con tu clave, y el servicio no puede hacer SSH a ningún sitio. Los archivos de /opt/notas son de notas. Para desplegar, tu usuario está en el grupo o copias con sudo -u notas. En el primer servidor, User=ubuntu es aceptable si la clave SSH es tuya y el grupo de seguridad no tiene el puerto 22 abierto al mundo entero.

tmux o screen no sustituyen a systemd. Sirven para no perder una sesión SSH mientras miras un log. El proceso de la app, si lo dejaste en esa sesión, muere al apagarse el portátil. Si ya te pasó, el síntoma es "en el servidor iba anoche". Pásalo al unit de arriba.

Errores frecuentes

Permission denied

Causa habitual: el archivo es de root y el proceso corre como ubuntu, o al revés. También una clave SSH con permisos abiertos (chmod de la .pem tiene que ser 600; si es 644, SSH se niega a usarla). Y un directorio sin permiso de ejecución: sin x no puedes cd, aunque puedas leer el nombre.

Arreglo:

ls -la /opt/notas
ls -la /opt/notas/.env

La columna del dueño tiene que ser el mismo usuario que User= del servicio. namei -l /opt/notas/.env muestra en qué carpeta del camino se pierde el permiso. No resuelvas con chmod 777. Para el .env, 600. Para la carpeta del proyecto, 755 y dueño correcto: sudo chown -R ubuntu:ubuntu /opt/notas.

command not found

Causa habitual: el paquete no está instalado, o está instalado y el PATH de systemd no es el de tu sesión SSH. Pasa con node instalado vía nvm: tu SSH lo encuentra y el servicio no, porque nvm se activa en .bashrc, que systemd no lee.

Arreglo: command -v node en la SSH te da la ruta real (/usr/bin/node o una ruta larga de nvm). Esa ruta completa va en ExecStart=. Mejor: instala Node en /usr/bin o /usr/local/bin y no uses nvm en el servidor. sudo apt install el paquete que falte (nginx, postgresql-client, redis-tools).

No space left on device

Causa habitual: logs, node_modules copiados varias veces, un pg_dump en el mismo disco, o la imagen de un apt a medias.

Arreglo:

df -h
sudo du -xh / --max-depth=1 | sort -h

du tarda. Empieza por /var y /home. Borra dumps viejos y logs ya rotados, no la base de datos. sudo journalctl --vacuum-size=100M recorta el journal. Después reinicia la app y comprueba que escribe. Si el disco está al 100 %, Postgres puede haberse parado para no corromperse: systemctl status postgresql antes de dar el problema por resuelto. Una copia en el mismo disco no te salva de este fallo; sácala, como en 08-postgresql.md.

El servicio no arranca con systemd

Causa habitual: error de sintaxis en el unit, ExecStart con una ruta que no existe, o el programa sale al instante porque falta una variable.

Arreglo, en este orden:

sudo systemd-analyze verify notas.service
journalctl -u notas -n 80 --no-pager
sudo -u ubuntu /usr/bin/node /opt/notas/src/server.js

El tercer comando corre igual que el servicio, en primer plano, y ves el error de Node (Falta PORT, EADDRINUSE, módulo no encontrado). status muestra 203/EXEC si la ruta de ExecStart está mal, y exited con código si Node arrancó y murió. Restart=on-failure reintenta; si muere siempre, journalctl se llena de los mismos renglones. Lee el primero, no el último.

Cómo comprobar

  1. ssh entra sin contraseña, con la clave.
  2. systemctl status notas dice active (running) después de cerrar la SSH y volver a entrar.
  3. curl http://127.0.0.1:3000/api/salud dentro del servidor responde. Desde tu casa todavía no tiene por qué: eso es el grupo de seguridad y Nginx.
  4. sudo reboot, esperas, vuelves a entrar y el servicio está otra vez active sin que tú lo arranques.
  5. .env está en 600 y no es legible por otros (ls -la).

Si esto no alcanza

man systemctl, man journalctl, man ssh. En la práctica: systemd service example, journalctl unit, ufw allow nginx.

El código de salida de systemd (203/EXEC, 217/USER) se busca literal.

En una máquina Linux tuya (WSL o la EC2 del siguiente archivo):

  • Entras por SSH o por la terminal de WSL.
  • La app arranca con systemd, no a mano.
  • Lees el log con journalctl y encuentras una línea que tú imprimiste.
  • Cierras la sesión, vuelves, y el proceso sigue.

AWS básico

AWS alquila máquinas, discos de red, nombres DNS y envío de correo. El mapa, en este tramo, pide cinco servicios y nada más: EC2 (la máquina), VPC (la red), S3 (archivos), Route 53 (el dominio) y SES (el correo). El resto del mapa de AWS es la siguiente biblioteca.

Esta ficha es la receta mínima de un solo servidor para la app de notas. No es una certificación.

Antes de crear nada

AWS cobra. La capa gratuita cambia con el tiempo, dura un periodo limitado en las cuentas nuevas y no cubre todo lo que parece "pequeño" (una IP elástica sin instancia asociada, un dominio, un buzón de SES fuera de la sandbox, un disco que olvidaste). Antes de pulsar Create:

  1. Entra en Billing y activa una alarma de presupuesto (aunque sea de unos pocos dólares).
  2. Elige la región y no la cambies a mitad (por ejemplo us-east-1 o la más cercana). Anótala. Los recursos de otra región parecen "desaparecidos".
  3. Practica antes el mismo montaje en local: Linux, Postgres, Redis, Node, Nginx. Si en local no arranca, en EC2 tampoco, y allí el reloj de la factura sigue.
  4. Al terminar la prueba del día, para la instancia. Si no vas a volver, termínala y borra el volumen, la IP elástica y el balanceador si creaste alguno. Esta receta no usa balanceador.

La consola web basta. La línea de comandos (aws) y Terraform repiten lo mismo cuando el clic ya lo entiendes; Terraform está en 18-ansible-y-terraform.md.

Cuándo usarlo y cuándo no

Úsalo cuando quieras que la app tenga una IP pública tuya y, más adelante, un dominio. Para enseñar el proyecto un fin de semana, un túnel o un PaaS salen más baratos; el mapa pide AWS, así que esta es la ruta de estudio, con el gasto controlado.

No subas la base de datos a un RDS "porque es lo serio" en este checkpoint. PostgreSQL va dentro de la misma EC2. RDS es otra caja, de otro mapa, y otra factura.

Básico

EC2, la máquina

  1. AMI: Ubuntu LTS.
  2. Tipo: el más pequeño de la capa gratuita de tu cuenta (t2.micro o t3.micro, el que la consola marque como free tier eligible en el momento de crearla). Si ninguno sale elegible, para y revisa el precio por hora antes de continuar.
  3. Par de claves: créalo, descarga el .pem una sola vez, chmod 600 en tu máquina. Sin ese archivo no entras. No lo subas a Git.
  4. Red: la VPC por defecto. Así existe una subred pública y una puerta de enlace a internet, que es lo que el mapa llama VPC en este nivel. No diseñes subredes privadas todavía.
  5. Disco: 8 o 16 GB gp3 bastan para la app de notas.
  6. Grupo de seguridad: un nombre notas-sg.

Reglas de entrada de notas-sg, y ninguna más:

PuertoOrigenPara qué
22Tu IP pública de hoy, /32SSH
800.0.0.0/0HTTP, para el certificado
4430.0.0.0/0HTTPS

Tu IP cambia si reinicias el router. Cuando SSH deje de entrar, actualiza la regla; no la abras a 0.0.0.0/0 para "salir del paso" y la dejes. No añadas 3000, 5432 ni 6379: Node, Postgres y Redis solo se ven desde dentro de la máquina. Nginx es quien habla con el exterior, en 15-despliegue.md.

Entra:

ssh -i ~/.ssh/notas.pem ubuntu@LA_IP_PUBLICA

El usuario de la AMI Ubuntu es ubuntu. En Amazon Linux sería ec2-user. Si dices "permission denied" con el usuario equivocado, no es la clave.

Dentro, el checkpoint de 13-linux.md: instalar, copiar la app, systemd.

VPC, lo que tienes que reconocer

No vas a crear una VPC nueva en el básico. Vas a saber leer la que ya usa la instancia:

  • La instancia está en una subred. Esa subred tiene una ruta 0.0.0.0/0 hacia un Internet Gateway. Si esa ruta no está, la máquina no sale a internet y tú no entras.
  • La IP pública no es la IP privada. SSH y Nginx usan la pública. DATABASE_URL usa 127.0.0.1, la de dentro, no la pública.
  • El grupo de seguridad es un firewall aparte de ufw. Los dos filtran. Si uno permite y el otro no, no entra.

Con eso se depura "la instancia no responde" sin dibujar una red de tres capas.

S3, archivos

S3 guarda objetos (archivos) en un bucket. Sirve para el pg_dump y para una imagen que suba un usuario. No sirvas la base entera desde S3 ni guardes el .env ahí sin cifrado y sin pensarlo: un bucket público se ha llevado más de un secreto.

  1. Crea un bucket con un nombre único global (notas-copias-tu-inicial-2026, no notas).
  2. Bloquea todo acceso público (la casilla de Block Public Access, las cuatro opciones).
  3. Región: la misma de la EC2, para no pagar cruce de regiones en una prueba.

Sube y baja desde la EC2. La instancia necesita un rol de IAM, no una clave de acceso pegada en el .env. En la consola: IAM, rol para EC2, política mínima que solo permita s3:PutObject, s3:GetObject y s3:ListBucket sobre el ARN de ese bucket, y asigna el rol a la instancia.

En la EC2, con AWS CLI instalada (sudo apt install awscli o el paquete v2 oficial):

pg_dump "postgres://notas@127.0.0.1:5432/notas" --format=custom --file=/tmp/notas.dump
aws s3 cp /tmp/notas.dump s3://notas-copias-tu-inicial-2026/notas.dump
rm /tmp/notas.dump
aws s3 ls s3://notas-copias-tu-inicial-2026/

rm local después de comprobar el ls. El dump tiene tus datos; no lo dejes en /tmp ni lo copies al repo.

Intermedio

Route 53, el dominio

Un dominio cuesta dinero todos los años, con o sin tráfico. Si todavía no quieres pagarlo, quédate en la IP pública y da por practicado el DNS más adelante. No registres un dominio "para una prueba de una hora".

Cuando lo tengas:

  1. La zona hospedada pública aparece al registrar el dominio en Route 53, o la creas y cambias los NS en el registrador donde ya lo habías comprado.
  2. Un registro A apunta el nombre (notas.example.com) a la IP pública de la EC2.
  3. Espera a que resuelva. dig notas.example.com desde tu máquina tiene que mostrar esa IP. Puede tardar minutos; si el TTL es alto y cambiaste un registro viejo, tarda lo que diga el TTL.

Una IP pública de EC2 cambia al parar y volver a arrancar, salvo que uses una IP elástica. La elástica, asociada a una instancia encendida, suele entrar en la capa gratuita de muchas cuentas; suelta y sin instancia, se cobra. Si vas a parar la máquina por las noches, o aceptas actualizar el registro A, o dejas la elástica y revisas la factura la primera semana.

El certificado HTTPS no lo pide Route 53. Lo pide Let's Encrypt en la propia máquina, en 15-despliegue.md, cuando el DNS ya apunta.

SES, correo

SES envía el correo de "se ha creado tu cuenta" o "restablece la contraseña". Las cuentas nuevas están en sandbox: solo puedes enviar a direcciones que hayas verificado una a una. Para el checkpoint basta verificar tu propio correo de destino y un remitente. Salir del sandbox es una solicitud a AWS; no hace falta para aprender.

  1. Verifica una identidad de correo (tu dirección) en la misma región de la app. La región de SES importa: la API de otra región no ve la identidad.
  2. En sandbox, verifica también el destinatario.
  3. El rol de la EC2, o un usuario IAM distinto del rol de S3, necesita ses:SendEmail. Puedes ampliar el rol de la instancia con esa acción si el mismo servidor envía el correo. No uses la clave raíz de la cuenta AWS.

Prueba desde la consola ("Send test email") antes de escribir código. Cuando eso llegue a la bandeja de entrada, el código es una llamada SendEmail con el SDK v3 (@aws-sdk/client-ses), desde el servidor, nunca desde el navegador: en el navegador las credenciales quedan expuestas. Remitente: la identidad verificada. Cuerpo: texto y HTML. No adjuntes el token de sesión en una URL sin caducidad; el enlace de restablecimiento caduca y es de un solo uso (una fila en Postgres, como el refresh).

Mira la carpeta de spam en la prueba. Un correo sin SPF, DKIM y DMARC cae ahí. En sandbox, SES ya firma con su dominio de prueba si usas el remitente verificado; al pasar a un dominio tuyo hay que publicar los registros que la consola de SES te muestra, en la misma zona de Route 53. Ese es el nivel de "el correo llega a otro buzón", no el de la primera prueba.

Avanzado

Lo que se rompe cuando la instancia es la única y alguien más la ve.

Copias. Un pg_dump diario a S3, con caducidad de objetos (lifecycle de 30 días) para no acumular dumps. Prueba un aws s3 cp de vuelta y un pg_restore en una base vacía una vez. Sin esa prueba, el bucket es una esperanza.

Disco y parches de la EC2. El disco de 8 GB se llena con logs y dumps locales. El síntoma está en 13-linux.md. Ampliar el volumen en la consola no agranda el sistema de archivos solo: después hay que growpart y resize2fs. Búscalo con esas dos palabras el día que lo necesites; no lo hagas "por si acaso" el primer día.

Puerta de SSH. Mejor que dejar el 22 abierto a tu IP para siempre: entra y trabaja, y cuando termines la temporada de estudio deja la regla. Una clave .pem robada del portátil es la llave de la máquina. Si se te filtra, bórrala en el panel de pares de claves, crea otra y sustituye ~/.ssh/authorized_keys en la instancia (con la sesión todavía abierta, para no echarte fuera antes de probar la nueva).

IAM mínimo. El rol de la instancia solo S3 de ese bucket y SES de envío. Nada de AdministratorAccess "para no perder el tiempo". La clave de acceso de tu usuario personal, si instalas aws configure en el portátil, no se copia a la EC2: allí el rol se asume solo. aws sts get-caller-identity dentro de la EC2 tiene que mostrar el rol, no tu usuario.

Apagado. Stop conserva el disco y puede conservar la IP elástica si la asociaste. Terminate borra la instancia. Un volumen marcado para no borrarse al terminar sobrevive y se sigue cobrando. Míralo en EC2, volúmenes, antes de dar la práctica por cerrada.

Alarmas. Además del presupuesto, una alarma de CPU no es prioritaria en este tamaño. Sí lo es la de costo y, cuando la app esté en serio, la de disco. El monitoreo del proceso es Monit, en la máquina, no CloudWatch obligatorio.

Errores frecuentes

La instancia no responde por SSH ni por HTTP

Causa habitual, en orden:

  1. La IP pública cambió porque paraste y arrancaste. Mira la consola, no el papel donde la anotaste.
  2. El grupo de seguridad no tiene el 22 desde tu IP actual, o el 80/443 para HTTP.
  3. ufw dentro de la máquina bloquea, aunque el grupo de seguridad permita.
  4. La subred no tiene ruta al Internet Gateway (si creaste una VPC vacía en vez de usar la de por defecto).
  5. Estás en la región equivocada de la consola y miras otra instancia.

Arreglo: en la consola, la instancia está running y las comprobaciones de estado pasan. Desde tu máquina, ssh -v -i notas.pem ubuntu@IP cuenta hasta dónde llega. Si ni siquiera conecta el TCP, es red (grupo de seguridad, IP, VPC), no la clave. Si conecta y dice Permission denied (publickey), es usuario o .pem. La clave correcta con el usuario ec2-user en una Ubuntu falla igual que una clave mala.

S3 AccessDenied

Causa habitual: el comando corre sin el rol (en tu portátil, sin credenciales, o en la EC2 antes de asociar el rol), la política no incluye el bucket exacto, o el bucket está en otra región y el CLI apunta a otra.

Arreglo: aws sts get-caller-identity y aws s3 ls s3://el-bucket. Si la identidad no es el rol, no estás donde crees. La política tiene que llevar el ARN del bucket en ListBucket (arn:aws:s3:::nombre) y el de los objetos en GetObject y PutObject (arn:aws:s3:::nombre/*). Son dos recursos distintos; con solo uno de los dos, ls o cp falla y el otro parece funcionar. Un bucket con Block Public Access sigue siendo usable por el rol: "acceso denegado" no se arregla haciendo el bucket público.

El dominio no abre la app

Causa habitual: el registro A apunta a una IP vieja, los NS del registrador no son los de la zona de Route 53, o apuntas el dominio a la IP y nadie escucha en el 80 (Nginx parado). El DNS y el servidor son dos capas.

Arreglo: dig notas.example.com +short tiene que imprimir la IP pública actual. Si no imprime nada, el problema es la zona o los NS, no Nginx. Si imprime la IP y el navegador no abre, curl -I http://ESA_IP desde tu máquina. Si la IP responde y el nombre no, espera al TTL o hay un proxy de más por medio. Si la IP no responde, vuelve al grupo de seguridad y a 15-despliegue.md.

El correo cae en spam o SES lo rechaza

Causa habitual del rechazo: sigues en sandbox y el destinatario no está verificado, el remitente no es una identidad verificada, o llamas a SES en otra región (US East vs Europe). El mensaje de la API lo dice (MessageRejected, Email address is not verified).

Causa habitual del spam: el dominio no tiene los registros DKIM que SES te pide, o el cuerpo parece un aviso genérico sin texto claro y sin un remitente reconocible.

Arreglo: envía la prueba desde la consola de SES, en la misma región, al correo que ya verificaste. Si la consola entrega y tu código no, compara región, identidad del Source y permisos del rol. Si la consola también cae en spam, publica DKIM antes de escribir más código. No intentes "esquivar" SES con el puerto 25 de la EC2: AWS lo bloquea por defecto y los correos de un VPS sin reputación se descartan.

Cómo comprobar

  1. SSH entra. Tras un sudo reboot, vuelve a entrar y systemd levanta la app.
  2. El grupo de seguridad no lista 5432 ni 6379 ni 3000.
  3. aws s3 ls del bucket de copias funciona dentro de la EC2 y un pg_restore de prueba recupera una fila.
  4. Si hay dominio, dig muestra la IP actual y el navegador abre Nginx.
  5. Si hay SES, un correo de prueba llega a tu buzón verificado.
  6. La alarma de presupuesto existe y sabes cómo parar la instancia.

Si esto no alcanza

Documentación, con el nombre del servicio: ec2 security group ssh, s3 block public access iam role, route 53 record type A, ses sandbox verify email identity.

El código de error (AccessDenied, MessageRejected) se busca literal junto al nombre del servicio.

Checkpoint — despliegue en AWS (medio día, con la factura vigilada)

Una EC2 Ubuntu que es solo tuya:

  • SSH restringido a tu IP.
  • La app de notas escucha por dentro y se abre por HTTP en la IP pública (HTTPS si ya tienes dominio; si no, el HTTP de este checkpoint es temporal y el candado es la ficha siguiente).
  • Un dump en un bucket privado y una restauración probada en una base de prueba.
  • La instancia parada o terminada si no la vas a usar esta semana, y los volúmenes sobrantes revisados.

Hecho cuando otra persona, con la clave, entra por SSH, ve la app en el navegador y tú puedes decir cuánto te va a costar dejarla encendida.

Despliegue

Desplegar es dejar la app completa respondiendo en una URL, con HTTPS, sin que tú tengas una terminal abierta. Las piezas son las de 12-app-completa.md. La máquina es la de 14-aws-basico.md o, para practicar sin factura, una Linux tuya en la red local. Los comandos son los mismos.

Nginx recibe el 80 y el 443 y reparte: lo que empiece por /api va a Node en el puerto 3000, el resto son los archivos de dist/. PostgreSQL y Redis no salen de la máquina.

Cuándo usarlo y cuándo no

Hazlo cuando el checkpoint de la app completa ya pasa en local. Desplegar antes solo copia un fallo a un sitio donde cuesta más ver los logs.

No despliegues con npm run dev, ni con Vite preview, ni abriendo el puerto 3000 en el grupo de seguridad "un momento". Ese momento se queda.

Básico

En la máquina, con el código ya en /opt/notas (un git clone de tu repo, o un git pull):

cd /opt/notas
npm ci --omit=dev
node src/migrate.js

migrate.js tiene que ver DATABASE_URL. Si todavía no existe el unit de systemd, exporta la variable en esa sesión o usa node --env-file=.env src/migrate.js. El .env está en el servidor, creado a mano, con secretos distintos a los de tu portátil.

El frontend se construye antes de copiarlo, en tu máquina o en el servidor. En el servidor hace falta que las devDependencies estén disponibles en el momento del build, así que una opción simple es construir en local y copiar solo dist/:

npm run build

Eso ocurre en la carpeta del frontend. Sube el contenido de dist/ a /opt/notas/public/ (scp -r dist/* ubuntu@IP:/opt/notas/public/). No subas node_modules.

Node tiene que poder servir salud en el 3000, y Nginx los estáticos. Si prefieres que Node no sirva archivos, Nginx apunta root a esa carpeta. Esta ficha lo hace así, para que Node solo sea la API.

/etc/nginx/sites-available/notas:

server {
  listen 80;
  server_name notas.example.com;

  root /opt/notas/public;
  try_files $uri $uri/ /index.html;

  location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}

try_files ... /index.html manda las rutas de React (/nueva) al index.html. Sin eso, recargar /nueva da 404 de Nginx aunque en el dev de Vite funcionara.

sudo ln -s /etc/nginx/sites-available/notas /etc/nginx/sites-enabled/notas
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

nginx -t tiene que decir ok antes del reload. Un reload con el archivo roto deja el servidor anterior, o lo tira, según el error: no lo saltes.

El unit de systemd es el de 13-linux.md. NODE_ENV=production va dentro del .env que ese unit carga. En producción la cookie lleva Secure, así que este HTTP básico es solo el puente hasta el certificado. No des por terminado el despliegue en HTTP si ya hay usuarios.

Comprueba desde la propia máquina:

curl -i http://127.0.0.1:3000/api/salud
curl -i http://127.0.0.1/api/salud

Los dos tienen que responder 200. El primero no pasa por Nginx. El segundo sí. Si el primero va y el segundo no, el fallo es Nginx, no Node.

Intermedio

HTTPS con Let's Encrypt. El dominio ya apunta a esta máquina (14-aws-basico.md). El puerto 80 es alcanzable desde internet, porque el validador de Let's Encrypt entra por ahí.

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d notas.example.com

Certbot reescribe el server de Nginx, escucha en el 443 y redirige el 80 al 443. Renueva solo con un timer de systemd. Compruébalo:

systemctl list-timers | grep certbot
sudo certbot renew --dry-run

--dry-run no sustituye el certificado. Confirma que el mecanismo de renovación está programado. Un certificado caduca a los 90 días y el síntoma es el candado roto, no un fallo de Node.

La app detrás de un proxy tiene que saber que la petición original era HTTPS, si alguna vez armas una URL absoluta. proxy_set_header X-Forwarded-Proto ya va en el básico. No redirijas tú dentro de Express a HTTPS si Nginx ya redirige: dos redirecciones se enredan.

Variables solo en el servidor. /opt/notas/.env con chmod 600, dueño el del servicio. Nombres mínimos:

PORT=3000
NODE_ENV=production
DATABASE_URL=postgres://notas:CONTRASEÑA_LARGA@127.0.0.1:5432/notas
REDIS_URL=redis://127.0.0.1:6379
JWT_SECRET=otro-secreto-distinto-al-de-tu-portatil

PostgreSQL en esa máquina no acepta contraseñas desde la red. En pg_hba.conf la línea de 127.0.0.1 puede ser scram-sha-256, y no hay línea para 0.0.0.0/0. listen_addresses se queda en localhost. Es el equivalente, dentro de la caja, a no abrir el 5432 en el grupo de seguridad.

Actualizar una versión, a mano, el día que todavía no hay CI:

cd /opt/notas
git pull
npm ci --omit=dev
node --env-file=.env src/migrate.js
sudo systemctl restart notas
curl -i http://127.0.0.1:3000/api/salud

El build del frontend, si cambió, se vuelve a generar y a copiar a public/ antes del restart. Si la migración falla, no reinicies a ciegas: el código nuevo puede no entender la base vieja, o al revés. Lee el error, que será uno de 08-postgresql.md.

Avanzado

Lo que se rompe a la segunda actualización, o el día que el disco se llena a las tres de la mañana.

Orden seguro, el mismo de la app completa, escrito como lista de despliegue:

  1. pg_dump a S3, o al menos a otro directorio, antes de migrar si ya hay datos de alguien.
  2. Migración compatible con el código que todavía está corriendo.
  3. Copiar public/ nuevo.
  4. systemctl restart notas.
  5. curl de salud, un login y un alta de prueba. El alta de prueba se borra después.
  6. Si el paso 5 falla, git checkout al commit anterior, npm ci, restart. Por eso el paso 2 no puede haber tirado una columna que el código anterior necesita. Si la tiró, "volver" ya no es un checkout: es un pg_restore. Practica ese caso en la base notas_prueba, no el día que te importe.

Dos procesos en el mismo puerto: un Node viejo que lanzaste a mano y el de systemd. ss -ltnp | grep 3000 muestra el PID. Solo debe haber uno, y su padre conceptual es systemd (systemctl status muestra el Main PID). Si matas el equivocado, systemd lo reintenta o, si era el manual, el servicio sigue bien. Mira el PID antes de kill.

Cabeceras mínimas en el server de Nginx, dentro del bloque que escucha 443:

add_header X-Content-Type-Options nosniff always;
add_header Referrer-Policy no-referrer always;

always las manda también en los errores. No copiar una lista enorme de cabeceras que no sabes explicar. La política de contenido (CSP) es el siguiente paso cuando ya no queden script inline; un CSP mal puesto deja la página en blanco y parece un fallo de React. Añádela en una ventana en la que puedas probar, no en el mismo minuto del primer HTTPS.

Copia de la configuración. /etc/nginx/sites-available/notas y el unit de systemd no están en el repo hasta que tú los copies a una carpeta deploy/ del proyecto, sin secretos. El .env no entra en esa carpeta. Ansible, en 18-ansible-y-terraform.md, es quien los escribe en el servidor cuando dejes de hacerlo a mano. Hasta entonces, una copia en el repo es lo que te permite rehacer la máquina.

Cliente real. curl https://notas.example.com/api/salud desde tu casa, y el navegador en una ventana privada: registro, alta, recarga. La ventana privada evita que una cookie vieja de localhost te engañe.

Errores frecuentes

502 Bad Gateway

Causa habitual: Nginx está vivo y Node no. El proxy no tiene a quién hablar. También: Node escucha en otro puerto, o escucha solo en un sitio que Nginx no usa. proxy_pass http://127.0.0.1:3000 con Node en el 3001 produce este síntoma. Un Node que escucha en 127.0.0.1 está bien para esta receta; un Node apagado, no.

Arreglo:

systemctl status notas --no-pager
curl -i http://127.0.0.1:3000/api/salud
ss -ltnp | grep 3000
journalctl -u notas -n 40 --no-pager

Si curl al 3000 falla, el problema es el servicio (variable, migración, puerto ocupado), no Nginx. Arranca ese hilo en 13-linux.md. Si curl al 3000 va bien y el navegador ve 502, nginx -t y el proxy_pass: tiene que ser http://127.0.0.1:3000, con el puerto, sin barra final si la location es /api/ y Express espera /api/.... Una barra de más recorta el camino y las rutas dejan de coincidir, a veces como 404 y a veces como 502 si el upstream ni responde. Cuando Node sí responde y la ruta no existe, Express devuelve su 404, no un 502. El 502 es "no hubo respuesta HTTP".

El candado no carga o el certificado falló

Causa habitual: el DNS no apunta a esta máquina, el 80 no es accesible desde fuera (certbot no pudo validar), el certificado venció porque el timer de renovación no corre, o el navegador entra por https:// a la IP en vez de al nombre. Un certificado de Let's Encrypt es para el nombre, no para la IP. Entrar por la IP da aviso de seguridad aunque el sitio con nombre esté bien.

Arreglo: dig notas.example.com +short y la IP pública coinciden. sudo certbot certificates muestra la fecha. Si caducó, sudo certbot renew con el 80 abierto. Si nunca se emitió, lee el error de certbot: connection refused es Nginx o el grupo de seguridad; NXDOMAIN o una IP distinta es Route 53. No firmes un certificado a mano "autofirmado" y lo dejes para los usuarios: el navegador les pedirá una excepción y las cookies Secure se comportan distinto según el cliente.

En el servidor faltan variables y en local no

Causa habitual: en local usas --env-file=.env y en el servidor el unit no tiene EnvironmentFile=, o apunta a otra ruta. También un .env con export PORT=3000, que systemd no interpreta como bash, y el valor queda mal. O copiaste el archivo y el servicio no se reinició.

Arreglo:

systemctl cat notas
sudo ls -la /opt/notas/.env
sudo -u ubuntu bash -c 'test -n "$PORT" && echo PORT-si || echo PORT-no'

Ese bash -c no carga el EnvironmentFile. Quien lo carga es el servicio. Para ver qué tiene el proceso, mira el arranque: la comprobación Boolean(process.env.PORT) de 07-nodejs.md, escrita en el log. No imprimas JWT_SECRET ni DATABASE_URL para "ver si están". Compara nombres en systemctl cat y en tu .env.example.

El build del servidor no coincide con el de tu máquina

Causa habitual: en el servidor quedó un dist/ o un public/ viejo, o npm install allí resolvió otras versiones porque faltaba el package-lock.json. También un git pull que no trajo el frontend porque viven en otro repo que no actualizaste.

Arreglo: anota el commit (git rev-parse --short HEAD) en las dos máquinas. Tienen que coincidir. Despliega el frontend con npm ci y npm run build usando el lock, no con npm install. Borra public/ antes de copiar el dist/ nuevo, para no dejar un assets/index-VIEJO.js que el HTML ya no referencia, ocupando disco y confundiéndote al buscar. En el navegador, ventana privada: el nombre del JS en el código fuente tiene que ser el del build que acabas de copiar.

Cómo comprobar

  1. curl https://notas.example.com/api/salud desde tu casa, no solo dentro del servidor.
  2. El navegador muestra el candado para ese nombre. Recargar en una ruta de React no da 404.
  3. Registro, alta, recarga con la sesión, y un segundo usuario que no ve la nota.
  4. ss no muestra 3000, 5432 ni 6379 en una dirección pública (0.0.0.0 en esos puertos es un problema; 127.0.0.1:3000 está bien).
  5. Tras sudo reboot, sin que entres por SSH, la URL vuelve a responder cuando la máquina termina de arrancar.

Si esto no alcanza

nginx proxy_pass, nginx try_files spa, certbot nginx, systemd EnvironmentFile.

El texto 502 Bad Gateway junto con nginx error log (/var/log/nginx/error.log) da la línea connect() failed, que es la confirmación de que el upstream no aceptó la conexión.

Checkpoint — despliegue (medio día)

La app completa en una URL:

  • HTTPS si tienes dominio. Si no lo tienes, HTTP en la IP, sabiendo que es temporal y que la cookie de producción no irá Secure hasta que haya HTTPS. Anótalo en tu nota de despliegue para no darlo por cerrado.
  • Node solo en localhost, Nginx delante.
  • Un git pull (o una copia nueva) más restart, con la migración aplicada, y la salud en verde.
  • Reboot de prueba y la URL sigue viva.

Hecho cuando apagas tu portátil y la URL sigue abriendo el login.

Monitoreo

Monitorear es enterarte de que la app murió, o de que el disco se está llenando, sin esperar a que alguien abra el navegador. El mapa separa dos cajas: Monit (el vigilante que reinicia un proceso) y el checkpoint de monitoreo (disco, logs, una señal cuando algo va mal).

Empieza por lo que ya tienes. systemd con Restart=on-failure y journalctl cubren el caso "el proceso se cayó". Monit entra cuando quieres una regla explícita (el puerto 3000 no responde, el disco pasó del 85 %) y un reinicio aunque el proceso haya quedado colgado sin morirse.

Cuándo usarlo y cuándo no

Úsalo en el servidor donde la app ya está desplegada. En tu portátil, durante el desarrollo, el --watch y la terminal alcanzan.

No montes un stack de métricas (Prometheus, Grafana, un SaaS) antes de tener el reinicio y el disco. Esas herramientas son el mapa de DevOps, no este checkpoint. Un correo de Monit, o una línea en el log que tú miras al día siguiente, es suficiente aquí.

Básico

Confirma que systemd ya reintenta. En el unit de 13-linux.md están Restart=on-failure y RestartSec=3. Prueba controlada:

sudo systemctl start notas
MAIN=$(systemctl show -p MainPID --value notas)
sudo kill "$MAIN"
sleep 5
systemctl status notas --no-pager

El estado tiene que volver a active y el PID nuevo no es el que mataste. Si no vuelve, el programa está saliendo con un código que systemd no considera fallo, o Restart= no está en el unit que de verdad corre (systemctl cat notas).

Salud HTTP, desde la propia máquina, para no depender de Nginx en esta prueba:

curl -fsS http://127.0.0.1:3000/api/salud

-f hace que curl termine con error si el código es 400 o más. /api/salud tiene que consultar la base, como en 12-app-completa.md. Un { ok: true } escrito a fuego dice que Node vive y calla si Postgres no.

Disco, cada vez que entres al servidor y, mejor, en un cron:

df -h /

Anota el porcentaje. Por encima de 80 % ya es momento de mirar /var/log antes de que el síntoma sea No space left on device.

Intermedio

Monit vigila el puerto y el disco, y reinicia el servicio. En Ubuntu:

sudo apt install monit

En Ubuntu, /etc/monit/monitrc ya define cada cuántos segundos corre Monit e incluye /etc/monit/conf.d/*. No repitas set daemon dentro del archivo de la app: un segundo set daemon hace fallar monit -t. El intervalo se cambia una sola vez en monitrc (60 segundos es un valor razonable).

/etc/monit/conf.d/notas:

check host api-notas with address 127.0.0.1
  if failed port 3000 protocol http request "/api/salud" status = 200 for 2 cycles
    then exec "/usr/bin/systemctl restart notas"

check filesystem root with path /
  if space usage > 85% then alert

check system localhost
  if memory usage > 90% then alert

La comprobación HTTP exige un 200. Un proceso vivo que responde 500 no cuenta como sano. for 2 cycles espera dos rondas fallidas antes de reiniciar, para no matar el proceso por un parpadeo. Reiniciar en cada fallo instantáneo, en bucle, es peor que el fallo: Postgres no se recupera si lo martilleas. Si monit -t se queja de la línea status, deja la comprobación de puerto y protocolo, y usa la salud desde el cron con curl -fsS mientras consultas la sintaxis de tu versión con man monit.

sudo monit -t
sudo systemctl enable --now monit
sudo monit reload
sudo monit status

monit -t es la sintaxis, igual que nginx -t. No recargues sin eso.

Alerta: Monit puede mandar correo si configuras un relay. En este checkpoint no hace falta abrir ese frente el mismo día. sudo monit status y el log /var/log/monit.log son la alerta local. Cuando SES ya envía correo (14-aws-basico.md), se puede añadir set alert tu@correo y un set mailserver. Hasta entonces, un cron que escribe el disco en el journal basta como segunda pieza:

echo '*/30 * * * * df -h / | logger -t disco' | sudo tee /etc/cron.d/disco-notas

logger manda la línea a journald. La lees con journalctl -t disco. El archivo de cron tiene que terminar en salto de línea. Si tee no lo dejó, el cron ignora el archivo.

Reinicio colgado. Un Node en un bucle infinito sigue con el proceso vivo: systemd no lo reinicia porque no murió, y el puerto a veces ni acepta conexiones. La regla de Monit sobre /api/salud sí lo reinicia. Compruébalo parando Postgres, no inventando un bucle: la salud debe pasar a 500, Monit debe ejecutar el restart, y en journalctl -u notas se ve el arranque nuevo. Luego vuelve a arrancar Postgres. Si Monit reinicia cada minuto mientras la base sigue caída, para Monit (sudo monit unmonitor api-notas) hasta arreglar la base, o el reinicio en bucle no te deja leer el error con calma.

Avanzado

Lo que se rompe cuando el vigilante está mal calibrado o nadie mira las alertas.

Reiniciar no arregla un fallo de configuración. Si falta JWT_SECRET, Monit reiniciará para siempre y el log se llenará. La regla avanzada es: si el servicio lleva N reinicios en unos minutos, deja de reiniciar y alerta. En el unit de systemd puedes acotar con StartLimitBurst=5 y StartLimitIntervalSec=300. Cuando se alcanza el límite, el servicio queda parado y status lo dice. Ese "parado a propósito" es más claro que un proceso que parpadea.

[Service]
Restart=on-failure
RestartSec=3
StartLimitIntervalSec=300
StartLimitBurst=5

Monit, a su vez, no debería lanzar systemctl restart si systemd ya se rindió. Mira status antes de forzar. Un reinicio manual (systemctl reset-failed notas y luego start) es la decisión tuya, cuando ya leíste el error.

Disco y logs. El tope de journald está en 13-linux.md. Monit avisa al 85 %; tú tienes que tener un sitio donde leer ese aviso. Una vez por semana, entra y mira monit status y df -h. Un monitoreo que no se mira es un archivo en /etc.

Qué no vigilar todavía: CPU media, "usuarios conectados", tiempo de cada ruta. Con un solo servidor, el puerto, la salud con base de datos, la memoria y el disco cuentan la historia. El día que una ruta concreta se vuelva lenta, el log de 07-nodejs.md (método, ruta, código, milisegundos) te dice cuál, sin otro sistema.

El vigilante también se cae. systemctl enable monit hace que vuelva tras un reboot. Compruébalo en el mismo reboot del checkpoint de despliegue: después de entrar, systemctl is-active monit imprime active.

No expongas el puerto de Monit (2812) a internet. Si activas su web, que escuche en 127.0.0.1 y entra por SSH. Un Monit abierto con la contraseña por defecto es una puerta para reiniciar tus servicios desde fuera.

Errores frecuentes

El proceso murió y nadie se enteró

Causa habitual: lo habías arrancado en una sesión SSH o con npm run dev, sin unit y sin Monit. Cerraste el portátil y se fue. O el unit no tiene Restart= y un error lo dejó inactive desde anoche.

Arreglo: systemctl status notas y journalctl -u notas --since "yesterday" --no-pager. Si no existe el unit, créalo. Si existe y está inactive (dead) sin reinicios, falta Restart=on-failure o systemd alcanzó el StartLimitBurst (en el log se lee start request repeated too quickly). En ese segundo caso, lee el error de Node, corrígelo, sudo systemctl reset-failed notas y start. Mata la costumbre de dejar node en primer plano dentro de tmux como si fuera el despliegue.

El disco se llenó de logs

Causa habitual: un console.log del cuerpo de cada petición, un Restart= en bucle con el mismo error de mil líneas, o Nginx en debug. El síntoma de disco de Linux es la consecuencia; aquí está la causa de los logs.

Arreglo:

journalctl --disk-usage
sudo journalctl --vacuum-size=100M
sudo du -xh /var/log --max-depth=1 | sort -h

Quita el log ruidoso del código y despliega esa versión. Recorta el journal como en 13-linux.md. Si Monit está reiniciando en bucle, unmonitor hasta que la salud pase en un arranque manual. Un vacuum sin quitar la causa solo aplaza el llenado unas horas.

Cómo comprobar

  1. Matar el PID de Node lo devuelve a active sin intervención, o Monit lo reinicia si lo dejas colgado sin puerto.
  2. curl -fsS http://127.0.0.1:3000/api/salud falla si paras PostgreSQL, y vuelve cuando lo arrancas. La salud no miente.
  3. monit status muestra la comprobación del host y la del disco.
  4. Tras un reboot, notas y monit están active.
  5. Sabes dónde leer el aviso (journal o monit status) y lo has abierto al menos una vez después de la prueba del kill.

Si esto no alcanza

monit check host port, systemd StartLimitBurst, journalctl vacuum-size.

La frase start request repeated too quickly se busca literal.

Checkpoint — monitoreo (45 a 60 minutos)

En el servidor del despliegue:

  • systemd reanima el proceso después de un kill.
  • /api/salud falla si la base está parada.
  • Monit (o el cron del disco, si Monit aún no envía correo) deja una prueba de que miraste el disco.
  • El puerto 2812 no está abierto al público.

Hecho cuando puedes decir, sin entrar al navegador de la app, si la API está viva y cuánto disco queda.

GitHub Actions

GitHub Actions corre comandos en una máquina de GitHub cada vez que empujas código. El checkpoint de CI/CD del mapa es: las pruebas se ejecutan solas y, si pasan, el cambio puede publicarse. Si no pasan, no se publica.

CI es la parte de "correr las pruebas". CD es la parte de "dejar la versión nueva en el servidor". Empieza por CI. Un CD que despliega pruebas rotas automatiza el accidente.

Cuándo usarlo y cuándo no

Úsalo cuando el repo ya está en GitHub y tienes al menos un comando que decide si el código está bien (npm test). Si todavía no hay pruebas, el primer workflow puede limitarse a npm ci y un arranque que compruebe que el archivo principal no tiene un error de sintaxis. Mejor una prueba de verdad, aunque sea una.

No metas el despliegue en el mismo workflow el primer día. Primero verde en las pruebas. El despliegue, cuando exista, solo corre en main y solo si las pruebas de ese mismo workflow pasaron.

Básico

Una prueba mínima que de verdad falla si rompes la validación. Con Vitest, que ya se nombró en 04-npm.md:

npm install --save-dev vitest

src/texto.js:

export function textoValido(valor) {
  const text = typeof valor === "string" ? valor.trim() : "";
  return text.length >= 1 && text.length <= 2000;
}

src/texto.test.js:

import { describe, expect, it } from "vitest";
import { textoValido } from "./texto.js";

describe("textoValido", () => {
  it("rechaza el vacío", () => {
    expect(textoValido("   ")).toBe(false);
  });
  it("acepta una frase", () => {
    expect(textoValido("Primera")).toBe(true);
  });
});
{
  "scripts": {
    "test": "vitest run"
  }
}

En local, npm test tiene que terminar con código 0. Actions no hace magia: corre eso mismo.

.github/workflows/ci.yml:

name: ci
on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test

La versión de Node es la LTS que usas en el servidor. Si el servidor tiene 20, escribe 20. No dejes que Actions corra en una versión y systemd en otra.

Sube el archivo a main. En la pestaña Actions del repositorio tiene que aparecer una ejecución verde. Si el repo es nuevo, Actions a veces pide que lo actives en los ajustes.

Un pull request con una prueba rota tiene que verse rojo y no se fusiona. Esa es la regla de protección de la rama, en GitHub: Settings, Branches, rule en main, exigir que el check test pase. Sin esa regla, el workflow avisa y tú puedes fusionar igual. Para el checkpoint, actívala.

Intermedio

El workflow de despliegue, separado del de pruebas, solo en main, y solo después de que ci haya pasado. La forma más simple de "pasó" es poner el job de deploy en el mismo archivo, con needs: test. Así no hay forma de desplegar si el job anterior falló.

Desplegar desde GitHub al servidor se hace por SSH. La clave privada es un secreto del repositorio, no un archivo del código. Genera un par solo para esto, en tu máquina:

ssh-keygen -t ed25519 -f notas-deploy -C "github-actions"

La pública (notas-deploy.pub) va a /home/ubuntu/.ssh/authorized_keys en el servidor. La privada se pega en GitHub: Settings, Secrets and variables, Actions, secreto SSH_KEY. Otros secretos: SSH_HOST (IP o dominio) y SSH_USER (ubuntu). No marques "debug" en el workflow para imprimirlos.

Añade un job al mismo archivo, o crea .github/workflows/deploy.yml que se dispare al terminar CI en main. Un solo archivo es más fácil de leer al principio:

name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build --prefix frontend
      - name: copiar y reiniciar
        uses: appleboy/scp-action@v0.1.7
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_KEY }}
          source: "frontend/dist/*"
          target: "/opt/notas/public"
          strip_components: 2

Revisa la versión de appleboy/scp-action en el registro de acciones el día que lo uses, y fija un tag. El source y strip_components dependen de cómo se llame tu carpeta: pruébalo una vez y mira qué quedó en /opt/notas/public. Un index.html en el sitio equivocado es el fallo más común de este paso.

El restart no va dentro de una acción opaca si puedes evitarlo. Un segundo paso con appleboy/ssh-action, también con la versión fijada, ejecuta en el servidor:

cd /opt/notas
git pull
npm ci --omit=dev
node --env-file=.env src/migrate.js
sudo systemctl restart notas
curl -fsS http://127.0.0.1:3000/api/salud

Para que ubuntu pueda reiniciar el servicio sin contraseña, una línea de sudoers específica, no NOPASSWD: ALL:

ubuntu ALL=(root) NOPASSWD: /usr/bin/systemctl restart notas

Archivo /etc/sudoers.d/notas, permisos 440, creado con sudo visudo -f /etc/sudoers.d/notas. visudo valida la sintaxis. Un sudoers roto te deja sin poder usar sudo.

El git pull en el servidor exige que el servidor pueda leer el repo (una deploy key de solo lectura). Es otra clave, distinta de la que Actions usa para entrar por SSH. Dos llaves, dos propósitos.

Si migrate.js falla, el curl no debería ejecutarse: encadena con && o deja que el script salga con código distinto de 0. Actions marca el job rojo y la versión vieja sigue corriendo solo si el restart está después del migrate y no se llegó a él. Orden: migrar, y solo entonces restart.

Avanzado

Lo que se rompe cuando el workflow es el único que sabe desplegar.

Entorno de pruebas parecido al real. npm test que no toca la base no detecta una migración mala. Un servicio de Postgres en el propio job sí:

services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: notas
      POSTGRES_USER: notas
      POSTGRES_DB: notas
    ports:
      - 5432:5432
    options: >-
      --health-cmd "pg_isready -U notas"
      --health-interval 10s
      --health-timeout 5s
      --health-retries 5

Y un paso DATABASE_URL=postgres://notas:notas@localhost:5432/notas node src/migrate.js antes de los tests que usen la base. El secreto de producción no entra en este job. La URL de prueba va escrita en el workflow porque no es secreta: usuario y clave de mentira, base que se destruye al terminar el job.

Secretos. ${{ secrets.SSH_KEY }} vacío no siempre falla al parsear el YAML: falla más tarde, con un error de autenticación confuso, o la acción recibe una cadena vacía. El síntoma de abajo lo cubre. No imprimas el secreto en un run: echo. Aunque GitHub intente enmascararlo, un base64 del secreto se cuela en el log. Quien tiene acceso de administrador al repo puede leer los secretos al editarlos; no los pongas en un issue ni en el chat.

Entornos y aprobaciones. En un repo solo tuyo sobra. Cuando haya más gente, el job deploy se ata a un environment de GitHub con un revisor obligatorio. Así CI corre en cada PR y CD espera un clic. Es la forma de no publicar un viernes por un push a main que no miraste.

No despliegues desde un pull request de un fork con los secretos disponibles. El evento pull_request desde forks corre con un token de solo lectura y sin secretos si no cambias la configuración. No cambies esa configuración para "que el PR de un desconocido pueda desplegar". El if de main y de push ya deja el deploy fuera de los PR. Déjalo.

Fijar acciones por tag o por SHA. @v4 se mueve dentro de la versión mayor. Para esta biblioteca es aceptable en actions/checkout y actions/setup-node, que son de GitHub. Una acción de un tercero (appleboy/...) se fija a un tag concreto y se actualiza el día que tú lo decidas, no sola.

Errores frecuentes

El workflow está rojo

Causa habitual: npm test falla, npm ci falla porque el lock no coincide con package.json, o un error de sintaxis del YAML (dos espacios de menos y el job ni empieza).

Arreglo: abre la ejecución, abre el job, lee el primer paso rojo, no el último. Copia el comando (npm test, npm ci) y córrelo en local en la misma versión de Node (node -v). Si en local pasa y allí no, compara la versión y si el job tiene la variable que la prueba espera. No pulses "re-run" a ciegas más de una vez: si el código no cambió, el resultado tampoco, salvo un fallo de red al hablar con el registro de npm. En ese caso el log dice ETIMEDOUT o ECONNRESET, y reintentar sí tiene sentido.

Si el YAML está mal, GitHub muestra el error arriba del workflow, antes de los pasos. Un tabulador en vez de espacios rompe el archivo. El editor tiene que mostrar espacios.

El secreto llega vacío

Causa habitual: el secreto está en otro entorno (environment) y el job no declara ese environment, o se creó en otro repositorio, u organización, y no en este. También el nombre no coincide: SSH_KEY en GitHub y secrets.SSH_PRIVATE_KEY en el YAML. Los nombres distinguen mayúsculas.

Arreglo: en el YAML, el nombre entre secrets. es exactamente el de la página de secretos. Un paso de diagnóstico temporal, que se borra después:

- run: test -n "$SSH_HOST" && echo host-presente || echo host-vacio
  env:
    SSH_HOST: ${{ secrets.SSH_HOST }}

Imprime "presente" o "vacío", nunca el valor. Si está vacío, créalo en este repo. Los secretos de un environment solo se ven si el job dice environment: production. Los de Dependabot y los de Actions son listas distintas.

El workflow no se dispara

Causa habitual: el archivo no está en la rama por defecto en la ruta .github/workflows/ci.yml (una carpeta workflow en singular no cuenta). O el on solo dice push a main y tú empujaste una rama. O Actions está desactivado en el repositorio. O el YAML no es YAML válido y GitHub lo ignora con un aviso en la pestaña.

Arreglo: en GitHub, abre el archivo en la rama que empujaste y confirma la ruta. La pestaña Actions lista los workflows reconocidos. Si no está, mira el aviso amarillo. Empuja un commit vacío solo cuando la ruta ya es correcta y quieres repetir el evento: git commit --allow-empty -m "Dispara CI" y git push. No lo hagas para tapar un test rojo.

Cómo comprobar

  1. npm test en local, en verde.
  2. Un push abre una ejecución y termina en verde.
  3. Un commit que rompe la prueba a propósito (en una rama) sale rojo, y main no se actualiza si la regla de protección está activa. Luego reviertes ese commit.
  4. Si ya hay deploy: el servidor queda en el commit nuevo (git rev-parse --short HEAD por SSH) y /api/salud responde. Un test rojo no cambia el servidor.

Si esto no alcanza

Documentación de GitHub: workflow syntax on push, using secrets in github actions, encrypted secrets, branch protection required status checks.

El mensaje del paso rojo, literal, más github actions.

Checkpoint — CI/CD (60 a 90 minutos)

  • Un test automático que falla si la validación del texto se rompe.
  • Un workflow verde en main.
  • La rama main protegida por ese check, o, si la cuenta de GitHub no te deja activar la protección, una nota tuya de no fusionar en rojo y una prueba de que viste el rojo en una rama.
  • Opcional y deseable: el job de deploy, con secreto, que reinicia la app solo cuando el test pasó.

Hecho cuando un push que tú no vigilas en la terminal igual ejecuta npm test, y sabes dónde mirar el resultado.

Ansible y Terraform

Ansible deja el servidor configurado igual cada vez que lo ejecutas: paquetes, unit de systemd, Nginx, la app. Terraform describe la infraestructura (la EC2, el grupo de seguridad, el bucket) en un archivo y la crea o la destruye. El mapa los separa: primero automatización (Ansible), después infraestructura (Terraform).

Los dos se practican cuando ya hiciste el montaje a mano una vez, en 13-linux.md, 14-aws-basico.md y 15-despliegue.md. Automatizar un montaje que no entiendes copia el error a un archivo más largo.

AWS sigue cobrando lo que Terraform cree. Un apply es un clic de "Create" con otro nombre.

Cuándo usarlo y cuándo no

Úsalos para poder tirar la máquina de práctica y volver a tenerla mañana sin repetir veinte pasos de memoria.

No hace falta Ansible para instalar Node en tu portátil, ni Terraform para crear un bucket que vas a usar una tarde. El checkpoint es rehacer el servidor de la app, no gestionar una empresa.

Se puede hacer lo mismo con scripts bash. El mapa pide estas dos herramientas; los archivos de abajo son el mínimo, no un curso de cada una.

Básico

Ansible, un solo servidor

En tu máquina (donde está el código), con Python 3:

pip install ansible

O el paquete de tu sistema. ansible --version tiene que imprimir un número.

Carpeta deploy/ansible/ en el repo. Nada de secretos. inventory.ini:

[web]
notas ansible_host=LA_IP ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/notas.pem

playbook.yml:

- name: preparar la app de notas
  hosts: web
  become: true
  tasks:
    - name: paquetes
      ansible.builtin.apt:
        name:
          - nginx
          - postgresql
          - redis-server
        state: present
        update_cache: true

    - name: carpeta de la app
      ansible.builtin.file:
        path: /opt/notas
        state: directory
        owner: ubuntu
        group: ubuntu
        mode: "0755"
ansible -i inventory.ini web -m ping
ansible-playbook -i inventory.ini playbook.yml

ping tiene que decir pong. Si no, es el síntoma de abajo y no tiene sentido seguir. become: true es sudo. El usuario ubuntu necesita poder hacer sudo, que en la AMI de Ubuntu ya puede.

La segunda ejecución del mismo playbook tiene que decir ok, no volver a instalar de cero ni fallar. Eso es idempotencia: correrlo dos veces deja el mismo resultado. Si una tarea "cambia" siempre, está mal escrita (por ejemplo un shell que añade una línea a un archivo cada vez). Prefiere el módulo (ansible.builtin.file, ansible.builtin.copy, ansible.builtin.template) al shell.

Terraform, un grupo de seguridad y poco más

Instala Terraform desde la documentación de HashiCorp (el paquete oficial), no un binario de un sitio al azar. terraform version imprime el número.

deploy/terraform/main.tf, región y AMI revisadas el día que lo uses. La AMI de Ubuntu cambia; no copies un ami-012345 de un ejemplo viejo. Búscala en la consola de EC2 al lanzar una instancia Ubuntu y pégala, o usa el data source de Canonical que esté vigente en la doc (terraform aws ami ubuntu). Si el data source falla, una AMI concreta de tu región, escrita en el archivo, es suficiente para el checkpoint.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_security_group" "notas" {
  name = "notas-sg"
  description = "ssh desde casa, http y https"

  ingress {
    description = "ssh"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["TU_IP/32"]
  }

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Sustituye TU_IP. No dejes 0.0.0.0/0 en el 22 "temporalmente" dentro de un archivo que vas a aplicar.

cd deploy/terraform
terraform init
terraform plan
terraform apply

plan es la lectura obligatoria. Tiene que decir que va a crear el grupo de seguridad y nada que tú no esperes. apply pide confirmación: escribes yes. Las credenciales son las de tu usuario IAM en tu máquina (aws configure o variables de entorno), con permiso para ese recurso, no la clave raíz, y no se commitean. terraform.tfstate contiene ids y a veces datos sensibles: está en .gitignore, igual que .env. Sin el state, Terraform cree que no hay nada y quiere volver a crear.

Para el checkpoint de infraestructura basta este grupo, o una EC2 además del grupo si aceptas el costo de dejarla unas horas. Si añades aws_instance, el plan tiene que mostrar un t2.micro o t3.micro que tú hayas elegido mirando el precio, un disco pequeño y este security group. Al terminar la práctica:

terraform destroy

destroy también enseña un plan. Léelo. Confirma que lo que va a borrar es la práctica, no un recurso con otro nombre que ya tenías en la cuenta.

Intermedio

Ansible termina lo que el playbook básico dejó a medias: el unit, Nginx y el .env a partir de una plantilla sin secretos dentro del repo.

deploy/ansible/templates/notas.env.j2:

PORT=3000
NODE_ENV=production
DATABASE_URL=postgres://notas:{{ db_password }}@127.0.0.1:5432/notas
REDIS_URL=redis://127.0.0.1:6379
JWT_SECRET={{ jwt_secret }}

Los valores viajan por variables de Ansible, en un archivo que no se versiona, deploy/ansible/secretos.yml, listado en .gitignore:

db_password: "cambia-esto"
jwt_secret: "cambia-esto-tambien"

En el playbook:

- name: entorno
  ansible.builtin.template:
    src: templates/notas.env.j2
    dest: /opt/notas/.env
    owner: ubuntu
    group: ubuntu
    mode: "0600"

Y el unit de systemd con ansible.builtin.copy hacia /etc/systemd/system/notas.service, seguido de:

- name: recargar systemd
  ansible.builtin.systemd:
    name: notas
    state: started
    enabled: true
    daemon_reload: true

state: started arranca si no está, y no reinicia si ya está. Para recoger un cambio de código hace falta restarted, y eso corta conexiones. Sé explícito: una tarea de restart que solo corre cuando tú la pides (--tags restart), no en cada playbook de "asegurarme de que los paquetes siguen".

Terraform, state remoto cuando dejes de ser la única persona. En solitario, el terraform.tfstate local, fuera de Git, alcanza si haces copia de ese archivo en un sitio privado (el bucket de S3 con acceso solo tuyo es el sitio natural). Si lo pierdes y los recursos siguen en AWS, no lances apply a ciegas: importar (terraform import) o borrar a mano en la consola lo que creaste, con calma. Dos states distintos queriendo crear el mismo notas-sg chocan con "already exists".

Un solo directorio de Terraform por entorno. No reutilices el de práctica, con su state, para "la de verdad" cambiando un nombre a mitad. Carpeta nueva, state nuevo, plan leído desde cero.

Avanzado

Lo que se rompe cuando el archivo manda sobre la consola y alguien cambia las dos.

No edites en la consola lo que Terraform ya controla. El siguiente plan querrá deshacer el clic (cerrar un puerto que abriste a mano, o volver a abrir uno que cerraste). Si el cambio de la consola era correcto, llévalo al .tf y deja que el plan quede en "no changes". Si era un experimento, deshazlo en la consola antes del siguiente apply.

prevent_destroy en el bucket de copias:

resource "aws_s3_bucket" "copias" {
  bucket = "notas-copias-tu-inicial-2026"
  lifecycle {
    prevent_destroy = true
  }
}

Así un destroy de un descuido falla al llegar al bucket en vez de borrar los dumps. Para destruirlo de verdad el día que cierres el proyecto, quitas el bloque, aplicas y luego destruyes. Es un paso extra a propósito.

Ansible y secretos. secretos.yml no entra en el repo. Un ansible-playbook con -v o -vvv puede imprimir el .env en tu terminal. No pegues esa salida en un issue. En CI, Ansible no corre con -vvv.

El playbook no hace git pull como root dentro de un directorio de ubuntu con llaves mezcladas. El despliegue de código sigue siendo el de 17-github-actions.md o un git pull como el usuario de la app. Ansible prepara la máquina; no sustituye al historial de Git.

Terraform y la IP de SSH. Tu IP cambia y el cidr_blocks queda viejo: no entras, y la tentación es abrir 0.0.0.0/0. Cambia la IP en el .tf, plan, apply. El plan solo debe tocar esa regla.

Prueba de destrucción. En la cuenta de práctica, terraform destroy y comprueba en la consola que la instancia y el grupo ya no están, y que el bucket con prevent_destroy sí está. Volver a crear es el checkpoint: apply y luego el playbook de Ansible, y la app queda como la dejaste documentada. Si ese recorrido solo funciona "porque la máquina vieja seguía ahí", no está automatizado.

Errores frecuentes

Ansible UNREACHABLE

Causa habitual: IP vieja, grupo de seguridad sin tu IP actual, clave distinta de la que usaste con ssh a mano, o ansible_user equivocado.

Arreglo: el mismo ssh -i ~/.ssh/notas.pem ubuntu@LA_IP tiene que entrar antes de repetir el playbook. Si SSH entra y Ansible no, compara ansible_ssh_private_key_file y el usuario del inventory con el comando SSH que sí funcionó. ansible -i inventory.ini web -m ping -vvv muestra a qué IP intentó hablar. No uses -vvv si el playbook ya incluye secretos; para el ping no hay secretos.

Error acquiring the state lock

Causa habitual: otro apply o plan sigue corriendo, o se cortó a medias y dejó el lock. Terraform crea un archivo de lock para que dos applies no escriban el state a la vez. Con state local, el lock es de tu máquina. Con state en S3, el lock está en DynamoDB (o en el mecanismo de la versión que uses) y sobrevive a cerrar la tapa del portátil.

Arreglo: espera a que el otro comando termine. Si estás seguro de que no hay otro (cerraste la terminal, solo estás tú), borra el lock como dice el mensaje, con el id que el propio error imprime. No borres terraform.tfstate para "quitar el lock": eso olvida los recursos. Después, terraform plan tiene que verse coherente con lo que hay en la consola de AWS.

Un apply quiere destruir un recurso que necesitas

Causa habitual: cambiaste el nombre del recurso en el .tf (Terraform lo entiende como "borra este y crea otro"), cambiaste un atributo que obliga a reemplazar (en las EC2, varios lo hacen, y el plan lo dice con forces replacement), o estás en el directorio y el state de otra práctica.

Arreglo: no escribas yes. Lee el plan línea a línea. Plan: 0 to add, 1 to change, 0 to destroy es muy distinto de 1 to destroy. Si el reemplazo es una EC2, vas a perder el disco de esa instancia salvo que el volumen tenga delete_on_termination = false y aun así la app se cae durante el cambio. Corrige el .tf para que el plan no destruya, o acepta el reemplazo después de un pg_dump restaurado en otra parte. terraform plan -out=plan.bin y terraform apply plan.bin aplican exactamente lo que leíste, no un plan nuevo calculado un minuto después.

Cómo comprobar

  1. ansible-playbook dos veces seguidas: la segunda no cambia paquetes ni permisos del .env (sigue en 600).
  2. terraform plan después de un apply dice que no hay cambios.
  3. El grupo de seguridad en la consola coincide con el archivo: 22 solo desde tu IP, sin 5432.
  4. terraform.tfstate y secretos.yml no salen en git status.
  5. Has leído un plan que destruía algo y has salido sin escribir yes, aunque fuera una prueba. Saber abortar es parte del checkpoint.

Si esto no alcanza

Ansible: ansible apt module, ansible template module, ansible systemd module, ansible unreachable.

Terraform: terraform plan, terraform state, terraform prevent_destroy, y el nombre del recurso AWS (aws_security_group, aws_instance).

El error de AWS que Terraform envuelve (InvalidAMIID, InvalidParameterValue) se busca literal.

Checkpoint — automatización e infraestructura (medio día, con la factura en mente)

  • Un playbook que deja Nginx, PostgreSQL, Redis, la carpeta y el unit listos en una Ubuntu a la que ya puedes entrar por SSH.
  • Un Terraform que crea el grupo de seguridad (y la instancia, si decides pagarla unas horas) y cuyo plan posterior está limpio.
  • .gitignore con el state y los secretos.
  • Al acabar la práctica de la instancia, destroy o stop consciente, y una mirada a la consola de facturación.

Hecho cuando puedes explicar qué harías si la EC2 desapareciera esta noche: aplicar Terraform, pasar Ansible, desplegar el commit que CI ya probó. Si algún paso solo está en tu memoria y no en un archivo, todavía no está hecho.

Depuración

Depurar es acortar el sitio donde vive el fallo hasta que solo quede una causa. El orden está en 00-metodo-sin-ia.md. Esta ficha es la caja de herramientas: qué mirar en cada capa y qué comando lo demuestra. El arreglo de cada error concreto sigue estando en su categoría; el índice es 00-indice-de-sintomas.md.

Cuándo usarlo y cuándo no

Ábrela cuando el síntoma no esté en el índice, o cuando la ficha del índice no coincida con lo que tú ves. Si coincide, no improvises otra teoría: aplica esa ficha.

No acumules console.log en todas las funciones "por si acaso" y los dejes. Cada log de diagnóstico se quita al terminar, o se convierte en el log corto de método, ruta, código y milisegundos de 07-nodejs.md.

Básico

El navegador. F12, y tres pestañas:

  1. Consola. El primer error rojo. Clic en el archivo y la línea de tu código, no en la de node_modules o de React, salvo que el mensaje solo exista allí.
  2. Red. Recarga con la pestaña abierta (si no, la petición de carga ya pasó). Filtra por Fetch/XHR. Entra en la petición de la API y lee, en este orden: URL completa, método, código, cabecera de petición Content-Type y Authorization, cuerpo de la petición, cuerpo de la respuesta.
  3. Elementos. El botón que "no hace nada" está en el DOM o no está. Un elemento con tamaño 0 o tapado por otro explica un clic perdido sin que haya error en la consola.

Reproduce una sola vez y anota esos cuatro datos de la petición (URL, método, código, primera línea del cuerpo). Con eso se entra al índice.

El servidor, en local. La terminal donde corre npm run dev es el otro lado de la misma petición. Si el navegador dice 500, la causa está impresa ahí. Si no hay ninguna línea nueva al pulsar el botón, la petición no llegó: URL, puerto o CORS. CORS se ve en la consola del navegador y la petición en Red aparece como error de red, a veces sin código. curl no sufre CORS: por eso es el paso siguiente, no un adelanto opcional.

curl.exe -i http://localhost:3000/api/salud

En bash es curl. En PowerShell, curl a secas puede ser otro comando; curl.exe es el de verdad.

Lee el código de arriba abajo en el manejador de esa ruta, no el proyecto entero. La pregunta es: ¿qué línea pudo producir este código HTTP?

Intermedio

Separar frontend y API con la misma petición que hace el navegador. Copia, desde la pestaña Red, "Copy as cURL" si el navegador lo ofrece, y ejecútala. Si no, reconstrúyela:

curl.exe -i http://localhost:3000/api/notas -H "Authorization: Bearer TOKEN"
  • Falla igual que en la pantalla: el frontend queda fuera. Sigue en Node, Postgres o Redis.
  • Funciona en curl y falla en la pantalla: compara origen, cookie (credentials), y la URL (proxy de Vite frente a localhost:3000 directo). Es el terreno de 12-app-completa.md.

Base de datos, con la misma SQL que crees que corre. En el manejador, la consulta es un texto con $1. Sustituye el parámetro a mano en psql, entre comillas, y mira si el error es el mismo:

psql "postgres://notas:notas@localhost:5432/notas" -c "SELECT id FROM notes WHERE user_id = 1"

Si psql dice que la tabla no existe y Node también, es migraciones. Si psql devuelve filas y Node dice que no hay notas, Node está conectado a otra base. Imprime en el arranque el nombre de la base, no la contraseña:

const base = new URL(process.env.DATABASE_URL);
console.log("base", base.pathname);

Redis: redis-cli GET notas:1 en el momento del fallo, no diez minutos después. La clave o está o no está. Las dos situaciones están en 11-redis.md.

Git, para saber qué cambió desde que funcionaba:

git status
git diff
git log --oneline -5

Si ayer iba y hoy no, el diff es la lista de sospechosos. No revises el proyecto completo: revisa esas líneas. git stash deja tu cambio aparcado y confirma si, sin él, el fallo desaparece. Si desaparece, el bug está en lo que apartaste. Vuelve con git stash pop y reduce el diff hasta una sola modificación. Es el "cambiar una sola cosa" del método, aplicado al historial.

En el servidor, los mismos comandos por SSH, contra 127.0.0.1, más el log:

journalctl -u notas -n 100 --no-pager
curl -i http://127.0.0.1:3000/api/salud

No depures el servidor desde el navegador de tu casa si aún no has hecho ese curl dentro de la máquina. El camino está partido en Nginx, DNS y certificado, y mezclarlos alarga el fallo. El orden está en 15-despliegue.md.

Avanzado

Cuando el fallo es intermitente o solo aparece con datos reales.

Una petición concreta, no "a veces falla". En el log corto (método, ruta, código, milisegundos) busca los 500 y los tiempos altos. Si no tienes ese log, añádelo antes de seguir teorizando: sin él estás depurando de memoria. La forma está en 07-nodejs.md.

Bisect, si sabes un commit bueno y uno malo y el fallo se reproduce:

git bisect start
git bisect bad
git bisect good abc1234

Git te deja en un commit intermedio. Pruebas. git bisect good o git bisect bad. Repites hasta que dice cuál fue el primer commit malo. Entonces git bisect reset y miras ese diff, no toda la historia. No lo uses si no puedes probar en cada parada: sin prueba, el bisect adivina.

Consulta lenta: EXPLAIN ANALYZE con los parámetros reales, en 08-postgresql.md. No optimices una ruta cuyo log dice 20 ms. El tiempo tiene que salir de un reloj, no de la sensación.

Condición de carrera. Dos altas duplicadas no se reproducen con un clic. Dos terminales a la vez, o el botón sin disabled, sí. Si solo pasa "cuando voy rápido", escribe el gesto exacto (doble clic, dos pestañas) en la nota de fallo antes de cambiar el código. El arreglo de la doble alta está en la API, con la transacción o con la clave de idempotencia, no en un setTimeout.

El fallo solo en producción. Lista de diferencias, y se tacha una por prueba:

DiferenciaCómo la igualas
Commit distintogit rev-parse --short HEAD en los dos sitios
Variable ausenteNombres, no valores, como en 15-despliegue.md
Migración sin aplicarSELECT filename FROM schema_migrations en las dos bases
Build viejo del frontendEl nombre del archivo en public/assets
Datos distintosUna fila mínima parecida a la de producción, en local, sin copiar datos personales si puedes evitarlo

Copiar la base de producción a tu portátil arrastra correos y hashes. Si lo haces para un bug que no reproduces de otra forma, bórrala al terminar, no la dejes en un dump dentro del repo, y no la subas a un bucket público.

Cuando lleves más de una hora sin una capa descartada, para y escribe la plantilla de 00-metodo-sin-ia.md. Casi siempre el atasco es haber cambiado tres cosas y no saber cuál probar.

Errores frecuentes de la propia depuración

Estas no son fallos de la app. Son formas de perder el rastro.

El log que miras no es el del proceso que recibe la petición

Causa habitual: dos Node, el de systemd y uno manual. El log de tu terminal está quieto y el de journalctl se mueve, o al revés.

Arreglo: ss -ltnp | grep 3000 y compara el PID con systemctl show -p MainPID --value notas. Lee el log de ese PID, no el de la terminal que quedó abierta desde ayer.

El navegador enseña una respuesta vieja

Causa habitual: un 304, un service worker de un experimento anterior, o una pestaña que no recargó el JS.

Arreglo: ventana privada, o recarga forzada. En Red, marca "desactivar caché" mientras las herramientas están abiertas. Si un service worker aparece en la pestaña Application, desregístralo: esta app no registra uno en las fichas, así que sería un residuo.

El console.log no sale y crees que esa línea no se ejecuta

Causa habitual: estás mirando la consola del navegador para un log que corre en Node, o al revés. O el proceso de Node es el viejo, sin tu log, porque --watch no reinició (un error de sintaxis lo deja en el arranque anterior).

Arreglo: escribe el log con un prefijo feo y único (ZZZ) y busca ZZZ en la terminal correcta. Si no está, ese proceso no tiene el archivo que estás editando. pwd y la ruta del npm run dev lo confirman.

Cómo comprobar

La depuración terminó cuando se cumplen las tres:

  1. Puedes repetir el fallo con un gesto de una frase.
  2. Un cambio de una sola cosa lo hace desaparecer.
  3. El caso vecino sigue funcionando (la otra ruta, el otro usuario, el curl sin navegador).

Si falta la 2, no des por cerrado el arreglo aunque la pantalla "ya se vea bien".

Si esto no alcanza

MDN: mdn network panel, mdn console. Node: nodejs debugging. Git: git bisect. PostgreSQL: postgresql explain analyze.

Busca el mensaje literal del primer error, entre comillas, más el nombre de la capa que ya no descartaste.

Checkpoint — un fallo, una nota (30 minutos)

Provoca a propósito uno de estos, y escríbelo con la plantilla del método, sin saltarte capas:

  • Puerto ocupado.
  • Tabla inexistente.
  • Token ausente.

Hecho cuando la nota nombra la capa, el comando que lo demostró (curl, psql o la consola) y el archivo de esta biblioteca que tiene el arreglo. No hace falta que el fallo sea un misterio: hace falta que el recorrido quede escrito, para el día en que sí lo sea.

Seguridad mínima

Esta ficha es el suelo, no un mapa de ciberseguridad. Son las decisiones que evitan los incidentes típicos de una app de notas recién publicada: contraseñas en claro, tokens robables, bases abiertas a internet y secretos en Git. El mapa largo de seguridad es otra biblioteca. Aquí se cruza con el índice, en las dudas de "¿esto se puede publicar así?".

Si un ejemplo de otra ficha y esta se contradicen, manda esta.

Cuándo usarlo y cuándo no

Léela antes de poner la app en una IP pública, antes del primer usuario que no eres tú, y en cuanto vayas a guardar una contraseña o una clave de AWS.

No la uses para aplazar el checkpoint local. En localhost, sin datos de nadie, el riesgo es menor, y aun así el hábito se coge aquí: hash, parámetros SQL, .env fuera de Git. Cambiarlo el día del despliegue es cuando se olvida.

Básico

Contraseñas. Nunca se guardan en claro, ni en un log, ni en el JWT, ni en un console.log "un segundo". Se guarda el hash de bcrypt con coste 12, como en 10-jwt.md. Quien vea la tabla users no puede leer la clave ni probarla en otro sitio a velocidad de diccionario sin pagar el coste del hash. bcryptjs evita tener que compilar nada en el servidor.

Comprobar con bcrypt.compare. No compares dos hashes con ===: formatos distintos del mismo secreto pueden no ser idénticos como texto, y además enseñas en el código un patrón que luego copias a tokens. Para el refresh opaco, el hash SHA-256 sí se puede comparar como texto porque tú lo generaste siempre igual; está en la ficha de JWT.

SQL. Toda entrada de usuario va en $1, $2, no concatenada. El ejemplo y el motivo están en 08-postgresql.md. Validar el tipo antes (número entero, texto con largo máximo) reduce basura; no sustituye al parámetro.

Secretos. .env en .gitignore. En el repo, .env.example solo con los nombres:

PORT=
DATABASE_URL=
REDIS_URL=
JWT_SECRET=

JWT_SECRET se genera con randomBytes, no con una frase del README. Uno distinto en tu máquina y en el servidor.

HTTPS en cuanto haya dominio. Sin él, la contraseña y la cookie viajan legibles en la red por la que entras. El certificado está en 15-despliegue.md. Hasta ese día, no pidas a otra persona que use la app desde una cafetería.

El navegador no es una frontera. Cualquiera puede mandar un POST con curl saltándose React. La validación y el user_id viven en el servidor.

Intermedio

Sesión. Access token corto en memoria. Refresh en cookie httpOnly, SameSite=Lax, Secure en producción, Path estrecho. El servidor guarda el hash del refresh, no el valor. Cerrar sesión borra la fila. Cambiar la contraseña borra todas las filas de ese usuario. El detalle, en 10-jwt.md.

No pongas el access token en localStorage. Un script inyectado lo lee; la cookie httpOnly no. Ese script entra si pintas notas con innerHTML o si cargas un paquete que no revisaste. textContent y JSX ({nota.texto}, que escapa) cierran el agujero de las notas. No bajes la guardia en un dangerouslySetInnerHTML "para el markdown de la nota": o no hay HTML de usuario, o lo filtras con una librería hecha para eso y aun así la cookie httpOnly es la red de fondo.

CORS. Origen explícito, o mejor el mismo origen vía Nginx, y no * con credenciales. Ver 09-api-rest.md.

Cabeceras de Nginx, las dos de 15-despliegue.md: X-Content-Type-Options: nosniff y Referrer-Policy: no-referrer. No añadas una CSP copiada de un blog el mismo día que enciendes el sitio.

Permisos de filas. WHERE id = $1 AND user_id = $2 en lectura, edición y borrado. El id no es un secreto: se prueba 1, 2, 3. Responder 404 cuando la fila es de otro evita confirmar que existe; está en la ficha de JWT.

Límite de login. Diez intentos por correo cada cuarto de hora, en Redis, código 429. Sin Redis disponible, el login se niega (503), no se deja abierto. Ver 11-redis.md.

Cookies y registro. chmod 600 el .env. El proceso no corre como root. Los puertos 5432, 6379 y 3000 no están en el grupo de seguridad ni en ufw. SSH solo desde tu IP.

Dependencias. npm audit de vez en cuando, sin --force automático. Actualiza el paquete que el aviso nombra, corre npm test, commitea lock y package.json juntos. Un paquete que no usas se desinstala: es superficie de menos.

Avanzado

Lo que se rompe cuando la app lleva semanas encendida y la cuenta de AWS tiene una tarjeta.

Claves de AWS. Rol de la instancia con S3 de un bucket y ses:SendEmail, nada de administrador. Sin claves de larga duración dentro de la EC2. La clave raíz de la cuenta no se usa para el día a día; activa el MFA de esa raíz el día que abras la cuenta y no generes access keys para ella. Si una access key tuya llegó a un repo, se desactiva en IAM aunque hayas borrado el commit. El orden está en 05-git-y-github.md.

Redis y Postgres solo en 127.0.0.1. Un listen_addresses = '*' más un grupo de seguridad amplio es una base pública. Los buscadores de internet encuentran esos puertos solos. No hace falta un atacante dedicado a tu proyecto.

Copias. pg_dump periódico a un bucket privado, con lifecycle para no guardarlos eternos, y un pg_restore probado. Una copia que nunca restauraste no cuenta. El dump tiene datos personales (correos): el bucket no se hace público "para descargarlo fácil". Lo bajas con el rol o con tu usuario IAM.

Cuenta de práctica y cuenta con usuarios reales, separadas, el día que dejes de estar practicando. Un terraform destroy en el directorio equivocado no debería poder llevarse la base de otras personas. prevent_destroy en el bucket de copias está en 18-ansible-y-terraform.md.

Actualizaciones del sistema (apt upgrade) en la EC2 con más regularidad que "cuando me acuerdo", y la app tiene que poder reiniciarse después. El monitoreo de 16-monitoreo.md te dice si no levantó.

Datos de más. No pidas nombre, teléfono o dirección para una app de notas. El correo y la contraseña alcanzan. Borrar la cuenta es un DELETE de sus notas y de sus sesiones, y luego del usuario, en una transacción. Si todavía no hay botón, no guardes tampoco un historial paralelo "por si acaso".

Registro de incidentes, en una libreta tuya, no en el repo: qué clave rotaste, qué día, qué servicio. La próxima vez no adivinas si la clave vieja sigue viva.

Lo que esta ficha no cubre y no debes inventar: guardar tarjetas, cumplir una normativa concreta, pentesting, o "dejar la contraseña en un comentario hasta el lunes". Si el producto llega a cobrar dinero, es otra biblioteca y, muy probablemente, un proveedor de pagos que no te deja tocar el número de tarjeta.

Errores frecuentes

Vas a guardar una contraseña

Arreglo: columna password_hash, bcrypt.hash(password, 12) en el registro, bcrypt.compare en el login, mínimo 10 caracteres, la misma frase de error si el correo no está y si la clave no coincide. No hay SELECT password en ninguna ruta. No hay log del cuerpo de POST /api/sesion. Si ya guardaste alguna en claro, trátalas como filtradas: borra esas filas o fuerza un cambio, y no las "conviertas" con un script que las loguee por el camino.

Vas a decidir dónde va el token

Arreglo: no va en localStorage ni en la URL. El access token va en memoria y en la cabecera Authorization. El refresh va en cookie httpOnly con las banderas de 10-jwt.md. Si todavía estás en el básico de una sola cadena JWT, asume que se pierde al recargar y la pantalla lo dice. Alargarla a 30 días para no perderla es el peor sitio: un robo dura 30 días y no hay fila que borrar.

Vas a abrir un puerto o un bucket

Arreglo: la lista permitida hacia internet es 22 desde tu IP, 80 y 443. Nada más. El bucket de copias y el de archivos de usuario llevan Block Public Access. Un archivo que el usuario deba descargar se entrega con una URL firmada de corta duración o a través de tu API, después de comprobar el user_id, no con el objeto público. aws s3 ls con el rol tiene que funcionar, y abrir la URL del objeto en una ventana privada sin estar logueado tiene que fallar.

Vas a meter una clave en el repositorio o en el workflow

Arreglo: si es un secreto, va a .env (servidor o portátil) o a los secretos de GitHub Actions, no al YAML, no a un run: echo, no a un issue, no a esta biblioteca. El workflow comprueba que el secreto está presente imprimiendo presente o vacío, como en 17-github-actions.md. Si ya se subió, se rota en el proveedor el mismo día y después se limpia el árbol. Rotar es lo que quita el acceso. El commit nuevo solo deja de repartirlo.

Cómo comprobar

  1. En psql, password_hash empieza por $2 y no se parece a la contraseña que escribiste.
  2. git status y git log -p -1 no contienen .env, ni AKIA, ni un JWT_SECRET= con valor.
  3. Desde una red que no es la tuya (o con el grupo de seguridad a la vista), los únicos puertos de entrada son 22 restringido, 80 y 443.
  4. El segundo usuario no lee la nota del primero ni adivinando el id.
  5. La cookie de refresh, en las herramientas del navegador, está marcada HttpOnly y, en producción, Secure.

Si esto no alcanza

OWASP, en este orden de búsqueda: owasp password storage bcrypt, owasp sql injection, owasp session management. MDN: mdn httpOnly, mdn content security policy cuando llegue el momento de la CSP, no antes.
